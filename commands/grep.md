# grep：从关键词搜索到正则匹配，日志里定位问题的那一行

> 很多人用了好几年 Linux，grep 永远只会一种用法——`grep ERROR app.log`，查完就走。其实 grep 是一台模式匹配引擎，它的真正价值不在"找到什么"，而在"怎么找、展示多少上下文、输出什么格式"——这些才是日常排障省时间的秘密。

## 一、你会遇到的场景

某天线上出问题了，你要查 `nginx` 的错误日志。这份日志一天 2GB，你 grep 了一下 `error`，终端刷屏了——成千上万行。你根本看不清错误是从什么时候开始的、前后发生了什么。

新手的做法：把结果复制到编辑器里慢慢翻。或者加 `| less`，一行一行往下翻。

而真正理解 grep 的人，会这样敲：

```bash
grep -n -B2 -A5 'Fatal error' /var/log/nginx/error.log | less
```

每个匹配行的行号一目了然，前后各有 2 行和 5 行上下文，你立刻能判断这个错误是不是关键信号、附近有没有伴随异常。

**这就是 grep 的核心价值：在文本流或文件中筛选匹配模式的行，并灵活控制输出格式和上下文——它既是过滤器，也是日志浏览器。**

## 二、它是怎么工作的——IO 模型

grep 的本质不是 `grep 关键字`，而是 `输入流 → 逐行匹配 → 命中输出`：

```
输入（文件 / stdin / 管道）
    │
    ↓ 逐行读入
    │
    ↓ 用模式（pattern）匹配这一行
    │   模式可以是：
    │   ├─ 普通字符串（默认 BRE——基本正则）
    │   ├─ 扩展正则（-E：ERE，+ ? | () 不用转义）
    │   ├─ 固定字符串（-F：不解析正则，纯字面量）
    │   └─ 多个模式（-e 或 -f 文件：命中任意一个即输出）
    │
    ↓ 命中 → 输出这一行（默认行为）
    │  未命中 → 跳过，读下一行
    │
    ↓ 输出方式：
    │   ├─ 默认：打印整行到 stdout
    │   ├─ -v：反转——打印不匹配的行
    │   ├─ -c：只打印匹配行数
    │   ├─ -l：只打印含匹配的文件名
    │   └─ -o：只打印匹配到的部分（不打印整行）
    │
输出：匹配行 / 计数 / 文件名 / 上下文
```

> 💡 理解了 IO 模型，`-v`（反转匹配）、`-c`（计数）、`-l`（列出文件名）、`-o`（只输出匹配部分）这些选项就自然出现了——它们控制的不是"找什么"，而是"怎么输出"。grep 的强大不在于正则（那是基本功），而在于**输出控制**——同样的搜索结果，换一个输出选项，用途完全不同。

## 三、语法骨架——先把句型刻进脑子里

```
grep  [选项]  [模式]  [文件...]
       ─┬─     ─┬─     ──┬──
       选件槽   模式槽     输入槽
```

属于**骨架模式 B**：`模式 + 对象`。同一模式的命令还有 sed——`sed '模式 命令' 文件`，句型几乎一样。grep 更纯粹：它只筛选，不编辑。

⚠️ **在讲具体能力之前，先排三个新手几乎必踩的雷：**

### 雷一：`-e` 不是"扩展正则"！扩展正则是 `-E`

```bash
# ❌ 错误理解：以为 -e 是 extended regex
grep -e 'error+' app.log    # 这不会用扩展正则匹配 "一个或多个 r"，-e 只是指定模式

# ✅ 扩展正则是 -E（或 egrep）
grep -E 'error+' app.log    # + 表示一个或多个 r，匹配 error、errorr、errorrr...
```

规则：**`-E` = Extended regex（扩展正则），`-e` = 显式指定一个 pattern。** 这大概是 grep 最容易混淆的两个选项。`-e` 的真正用途是两个场景：① 指定多个模式（OR 逻辑）；② 模式以 `-` 开头时防止被当成选项。

```bash
# -e 的正确用法：多个模式（命中任意一个即输出）
grep -e 'ERROR' -e 'FATAL' -e 'PANIC' app.log

# -e 的正确用法：模式以 - 开头
grep -e '-v' file.txt    # 查找字面量 "-v"，不加 -e 的话 grep 会把 -v 当成自己的选项
```

> ⚠️ **这个误解太普遍了。** `-e` 是"expression"（追加一个模式表达式），`-E` 是"Extended"（扩展正则语法）。两个字母，完全不同的含义。

### 雷二：`grep` 默认是 BRE（基本正则），不是你习惯的正则

```bash
# ❌ 以为这些正则符号可以直接用
echo 'hello     world' | grep 'hello[ ]+world'    # ❌ + 在 BRE 里是字面量，不匹配
echo 'hello world' | grep 'hello[ ]+world'         # ❌ 还是不对

# ✅ 用 -E 切换到扩展正则（ERE），和大多数语言的正则行为一致
echo 'hello     world' | grep -E 'hello +world'    # ✅ 匹配多个空格
```

**默认 BRE 里，`+` `?` `|` `()` `{}` 都要前面加反斜杠才有特殊含义。** 这和 Python/JavaScript/awk 的默认正则行为完全不同。**养成习惯：用 grep 时无脑加 `-E`，正则就和你预期的一样了。** 唯一的例外是：当你要精确匹配字面量（不解析正则）时，用 `-F`（fixed strings）而不是 `-E`。

### 雷三：`grep pattern > file` 会清空文件——别把输出重定向回输入文件

```bash
# ❌ 灾难：重定向 > 会先清空文件，然后 grep 读一个空文件，最后 file.txt 空了
grep 'ERROR' app.log > app.log

# ✅ 用临时文件，或者用 -i 写入另一个文件
grep 'ERROR' app.log > errors-only.log
```

这个坑不是 grep 特有的，但 grep 的使用场景（过滤后写回原文件）让这个错误特别容易发生。**永远不要把 grep 的输出重定向到它正在读的文件。**

## 四、核心能力逐轴拆解

grep 的能力沿 5 个轴展开。不要背选项——每个轴回答一个具体问题，各轴正交，自由组合。

| 能力轴 | 问题 | 选项 |
|--------|------|------|
| 匹配轴 | 用什么规则找？ | `-E`(扩展正则)、`-F`(固定字符串)、`-i`(忽略大小写)、`-w`(全词匹配)、`-x`(整行匹配)、`-e`(多模式)、`-f`(从文件读模式) |
| 输出轴 | 输出什么内容？ | `-n`(行号)、`-c`(计数)、`-l`(文件名)、`-o`(只输出匹配部分)、`-v`(反转) |
| 上下文轴 | 命中行前后展示多少？ | `-A`(后N行)、`-B`(前N行)、`-C`(前后各N行) |
| 范围轴 | 搜哪些文件？ | `-r`(递归)、`--include`/`--exclude`(文件过滤) |
| 控制轴 | 怎么控制行为？ | `-m`(最早N个匹配后停止)、`-q`(安静模式)、`-a`(把二进制当文本) |

---

### 轴 1：匹配轴——"用什么规则找？"

> 场景：日志里大小写混用——ERROR、Error、error 都出现了，你想一刀全捞出来。

```bash
# 忽略大小写——最常用的组合
grep -i 'error' app.log

# 全词匹配——只想找 cat，不想匹配 scatter 或 concatenate
grep -w 'cat' files.txt

# 扩展正则：匹配 IP 地址
grep -Eo '[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}' access.log

# 固定字符串——模式本身含正则特殊字符时不用转义
grep -F '[ERROR]' app.log       # 找字面量 "[ERROR]"，而不是匹配 [] 字符类

# 多模式（OR 逻辑）——三种方式
grep -e 'ERROR' -e 'FATAL' -e 'PANIC' app.log      # 方式一：-e 多次
grep -E 'ERROR|FATAL|PANIC' app.log                  # 方式二：扩展正则的 |
printf 'ERROR\nFATAL\n' > /tmp/pats && grep -f /tmp/pats app.log  # 方式三：从文件读

# 整行匹配——不要部分匹配
grep -x 'exact line' file.txt
```

> 💡 正则三种模式的选择原则：**日常用 `-E`**（和 Python/JS 习惯一致），**模式含正则特殊字符时用 `-F`**（不用写一堆反斜杠），**搜索简单单词时用默认**（BRE 足够且不需要 `-E` 的开销）。

---

### 轴 2：输出轴——"输出什么内容？"

> 场景：你不想看匹配行本身——你只想知道"匹配了几行"或者"哪几个文件里有"。

```bash
# 统计匹配行数（非匹配次数——一行匹配多次也只算一次）
grep -c 'ERROR' app.log

# 列出含匹配的文件名（不打印匹配内容）
grep -rl 'TODO' src/

# 列出不含匹配的文件名（-L = -l 的反转）
grep -rL 'Copyright' src/

# 显示行号——排障必备
grep -n 'exception' app.log

# 只输出匹配到的部分（不是整行）
grep -o '[0-9]\{1,3\}\.[0-9]\{1,3\}\.[0-9]\{1,3\}\.[0-9]\{1,3\}' access.log

# 反转匹配——输出所有"不是"的行
grep -v '^#' config.ini           # 去掉注释行
grep -v '^[[:space:]]*$' file     # 去掉空行（含空格的行）
```

> ⚠️ **`-c` 统计的是匹配的"行数"，不是匹配的"次数"。** 如果一行里有三个 `error`，`-c` 只算一次。如果需要统计匹配次数，用 `grep -o | wc -l`。

```bash
# -c：匹配了几行
echo 'error error error' | grep -c 'error'    # → 1（只有一行）

# -o + wc：匹配了几次
echo 'error error error' | grep -o 'error' | wc -l   # → 3
```

---

### 轴 3：上下文轴——"命中行前后展示什么？"

> 场景：排查故障时，你很少只关心报错那行——你需要看错误前后的上下文来判断原因。

```bash
# 显示匹配行后面 5 行（After）
grep -A5 'Exception' app.log

# 显示匹配行前面 3 行（Before）
grep -B3 'Exception' app.log

# 显示前后各 2 行（Context）
grep -C2 'Exception' app.log
```

> 💡 这三个选项是 grep 的"被严重低估的能力"。默认的 grep 只给你匹配行，你永远不知道错误前面是不是有个 `WARN`、后面是不是有堆栈。**排障时养成习惯：`grep -C3` 或者 `grep -B2 -A10`**，上下文能节省大量翻日志的时间。而且输出中会用 `--` 分隔不同匹配块，阅读体验比全量日志好得多。

---

### 轴 4：范围轴——"搜哪些文件？"

> 场景：你想在一个项目里搜所有 `.go` 文件，但不搜 `vendor/` 目录和 `.pb.go` 生成文件。

```bash
# 递归搜索整个目录
grep -r 'func main' src/

# 限定文件类型
grep -r --include='*.go' 'func main' src/

# 排除目录
grep -r --exclude-dir='vendor' --exclude-dir='.git' 'pattern' src/

# 排除特定文件
grep -r --exclude='*.pb.go' 'pattern' src/
```

> 💡 `--include` 和 `--exclude` 是 GNU 扩展，但在 BSD grep（macOS）上也部分支持。它们比 `find ... | xargs grep` 更简洁，但 `find + grep` 在跨平台脚本里更可靠。一个判断原则：**交互式使用直接用 `--include`/`--exclude`，写脚本用 `find | xargs grep`。**

---

### 轴 5：控制轴——"怎么控制搜索行为？"

> 场景：文件太大，你只想要前 10 个匹配就停；或者你只需要知道"有没有"（在脚本里用退出码判断）。

```bash
# 前 N 个匹配后停止——适合大文件快速抽样
grep -m10 'ERROR' huge.log

# 安静模式——不输出任何内容，只返回退出码（0=找到，1=没找到）
if grep -q 'healthy' /var/log/health.log; then
    echo "service is up"
fi

# 把二进制文件当文本处理
grep -a 'pattern' somefile.bin
```

> 💡 `-q` 在 shell 脚本里极其常用——它不产生任何输出，只是告诉你"找到了没有"。配合 `&&` 和 `||` 可以写出非常干净的检查逻辑。而且 `grep -q` 在找到第一个匹配后就会停止扫描（性能优化），比 `grep | wc -l` 快得多。

## 五、Pipeline 组合——grep 是管道的第一道筛子

grep 在设计上就是管道的完美一环——它接受文本流、输出文本行，天然做"第一道筛选"：

```
cat huge.log
    │  输出：所有日志行（可能几百万行）
    ↓
grep 'ERROR'          （第一道筛子：只看 ERROR，筛掉 99%）
    │  输出：只含 ERROR 的行（可能几千行）
    ↓
grep -v 'timeout'     （第二道筛子：排除已知的 timeout 噪音）
    │  输出：排除超时后的错误（可能几百行）
    ↓
cut -d' ' -f5-        （提取关键字段）
    │
    ↓
sort | uniq -c | sort -rn | head   （统计 + Top N）
```

```bash
grep 'ERROR' huge.log | grep -v 'timeout' | cut -d' ' -f5- | sort | uniq -c | sort -rn | head -10
```

> 💡 这里能串起来的关键是：grep 输出的是完整的文本行（和输入格式完全一致），所以可以用多个 grep 级联筛选。**渐进式过滤** 是 grep 管道组合的核心思想——不是一次写一个大正则匹配所有条件，而是用一个长长的管道，每一步去掉一部分噪音，最后只剩下你真正要的信号。

**一个更高级的经典组合：find + xargs + grep**

```bash
# 在所有 .go 文件中搜索，排除 vendor
find . -name '*.go' -not -path '*/vendor/*' -print0 | xargs -0 grep -n 'TODO'
```

这里 grep 的角色从"行过滤器"变成了"文件内容扫描器"，输出格式是 `文件名:行号:内容`——天然适合作为下一步（如 vim 快速跳转）的输入。

## 六、踩坑清单

- **坑一：`-e` ≠ `-E`** → `-e` 是追加模式，`-E` 是扩展正则。扩展正则是大写的 `-E`。
- **坑二：默认 BRE 里 `+` `?` `|` `()` `{}` 都只是字面量** → 用 `-E` 或在这些符号前加 `\`。无脑用 `-E` 是最简单的解决方案。
- **坑三：`grep pattern file > file` 会把文件清空** → 输出重定向会先截断文件，grep 读到空文件。用 `grep pattern file > newfile` 或 `sponge`。
- **坑四：`-c` 统计的是行数不是匹配次数** → 一行多个匹配只计一次。要统计匹配次数用 `grep -o | wc -l`。
- **坑五：`-r` 不加 `--include` 会搜所有文件** → 包括二进制文件（grep 会输出 "Binary file matches" 然后跳过，但你不知道它跳过了什么）。加 `-I` 跳过二进制，或加 `-a` 强制当文本处理。
- **坑六：搜索以 `-` 开头的模式时忘了 `-e`** → `grep -- -foo file` 或 `grep -e '-foo' file`，否则 `-foo` 会被当成选项。
- **坑七：管道里用 `grep` 做条件判断时忘了退出码** → `grep` 在找到时返回 0，找不到返回 1。`grep -q` + `&&`/`||` 是 shell 脚本里最干净的条件判断模式。

## 七、什么时候该换工具

| 场景 | 用什么 | 为什么 |
|------|--------|--------|
| 筛选匹配模式的行、查看上下文、统计匹配 | grep | 这正是 grep 的设计领域——轻量、快速、输出控制灵活 |
| 对匹配的行做编辑（替换/删除） | sed | grep 只筛选，sed 能做编辑 |
| 按列统计、跨行聚合 | awk | grep 没有字段和算术能力 |
| 实时追踪日志文件 | `tail -f \| grep` | grep 本身不追踪文件变化 |
| 搜索文件名（不是文件内容） | find | `find -name` 比 `grep -rl` 快得多 |
| 搜索二进制文件内的模式 | `strings \| grep` | grep 对二进制不友好，先用 strings 提取可读文本 |
| 模糊搜索（拼写容错） | ag / ripgrep / fzf | grep 做精确正则匹配，不支持模糊匹配 |

## 八、换个命令你会了吗？

grep 属于**骨架模式 B**：`模式 + 对象`。同一模式的命令还有：

- **sed**：`sed '地址 命令' 文件`——地址就是 grep 的 pattern + 行号，命令就是 s/d/p。学完 grep 再看 sed 的地址部分，理解成本几乎为零
- **awk**：`awk '/pattern/ {action}' 文件`——awk 的模式部分就是 grep（甚至是直接复用的正则语法），动作部分是 grep 不具备的计算能力

学完 grep，你其实已经掌握了"模式→筛选→输出"这一类命令的核心思维。**下次看到 sed 的地址写法，你会发现 `sed '/error/d'` 就是 `grep -v error`——它们共享同一种正则引擎，只是输出方式不同：grep 打印命中的行，sed 对命中的行执行命令。**

---

> **核心观点：** 学 grep 不是为了记住 `grep pattern file` 这个固定用法，而是理解它的 **IO 模型**（逐行匹配 → 命中输出）和 **5 个能力轴**（匹配、输出、上下文、范围、控制）。一旦这两个立住了，任何"从文本里筛出信号"的需求你都能从轴里选出组合，填入骨架，命令自然生成。
>
> grep 真正的价值不在正则（那是所有文本工具的基本功），而在**输出控制**——`-c` 统计、`-l` 定位、`-v` 排除噪音、`-C` 展示上下文。这四个选项决定了你是在"找东西"还是在"分析数据"。
>
> 你平时用 grep，是不是也只敲 `grep 关键字` 就回车了？
