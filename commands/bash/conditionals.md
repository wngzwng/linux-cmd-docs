# 为什么 bash 条件表达式坑最多？`[`、`[[`、`((` 90% 的人从一开始就用错了

> 很多人写了上百个 bash 脚本，`if` 后面的括号从来都是「凭感觉加」——能跑就行，不能跑就加引号、加空格、换写法，折腾半天还是不知道为什么。其实这三个括号根本不是同一种东西：**一个是命令，一个是关键字，一个是算术黑箱**。搞不清它们的本质区别，早晚会在生产环境翻车。

## 一、你会遇到的场景

凌晨两点收到告警：部署脚本执行失败。你打开日志一看：

```
./deploy.sh: line 23: [: =: unary operator expected
```

第 23 行是这样的：

```bash
if [ $STATUS = "ready" ]; then
    deploy
fi
```

你明明在脚本开头设置了 `STATUS="ready"`，为什么报错？你登录服务器手动跑了一下 `echo $STATUS`——空的。原来这个变量是从一个可能失败的 API 请求里取的，偶尔会空。

更让你困惑的是：用了好几年 bash，你知道 `[ ]`、`[[ ]]`、`(( ))` 都能写条件，但每次换一个写法，行为就不一样。加不加空格？要不要引号？为什么有的地方用 `=` 有的地方用 `==`、有的地方用 `-eq`？

**这三个括号不是三种"写法"，而是三种本质不同的求值机制。** 理解这一点之后，你根本不需要背"什么时候用什么"——每种括号的能力边界是固定的。

## 二、概念模型——三个括号，三种本质

先看一张对比表，把你脑子里的混乱一次性理清：

```
┌─────────┬──────────────┬────────────────┬──────────────────┐
│         │    [ ]       │    [[ ]]       │    (( ))         │
├─────────┼──────────────┼────────────────┼──────────────────┤
│ 本质    │ 命令（test） │ bash 关键字    │ bash 算术上下文  │
│ POSIX   │ ✅ 是       │ ❌ 否          │ ❌ 否            │
│ 单词拆分 │ ✅ 会拆分   │ ❌ 不拆分      │ ❌ 不拆分（纯算术）│
│ 路径展开 │ ✅ 会展开   │ ❌ 不展开      │ ❌ 不展开         │
│ 空变量   │ ⚠️ 语法错误 │ ✅ 安全处理    │ ✅ 安全处理       │
│ 短路求值 │ ❌ 不短路   │ ✅ 短路        │ ✅ 短路           │
│ 模式匹配 │ ❌ 无       │ ✅ == 通配符   │ —                 │
│          │             │    =~ 正则     │                   │
│ 退出码   │ 0=真 1=假  │ 0=真 1=假     │ 表达式≠0 → 真     │
│          │             │               │ 表达式=0 → 假     │
└─────────┴──────────────┴────────────────┴──────────────────┘
```

> 💡 最关键的认知：**`[` 是一个命令，不是语法。** `/usr/bin/[` 这个文件真实存在，它和 `test` 是同一个程序。`[` 要求最后一个参数必须是 `]`，仅此而已——其他方面它就是一个普通命令。这意味着 shell 在调用 `[` 之前，会先对它做**单词拆分**和**文件名展开**——正是这两点导致了 90% 的坑。

而 `[[` 和 `((` 是 bash 的**关键字**（compound command），bash 在解析它们时，知道这是条件上下文，所以**不做单词拆分、不做文件名展开**。这是 `[[` 比 `[` 安全的根本原因。

## 三、语法骨架——先把句型刻进脑子里

```
# 文件/字符串测试
[ 表达式 ]               ← test 命令，必须用空格包围括号
[[ 表达式 ]]             ← bash 关键字，空格也是必须的
test 表达式              ← [ ] 的另一种写法，不需要 ]

# 算术测试
(( 算术表达式 ))          ← bash 算术上下文，C 语言风格语法
```

属于**骨架模式 B**：`条件表达式 → 退出码`。本身不产生输出，只通过退出码（`$?`）表达真/假，供 `if`/`while`/`&&`/`||` 消费。

⚠️ **在讲具体能力之前，先排四个新手几乎必踩的雷：**

**雷一：`[` 和 `]` 左右必须有空格——因为 `[` 是命令名**

```bash
# ❌ 错误：shell 看到的是命令名 "[-f"（不存在）
if [-f /etc/passwd ]; then echo "yes"; fi
# bash: [-f: command not found

# ✅ 正确：[ 是命令，-f 是第一个参数，] 是最后一个参数
if [ -f /etc/passwd ]; then echo "yes"; fi
```

`[` 不是标点符号，是命令名。就像你写 `ls -l` 不能写成 `ls-l` 一样，`[ -f` 不能写成 `[-f`。

**雷二：`[ ]` 中未加引号的变量为空时，会变成语法错误**

```bash
# ❌ 错误：$x 为空时展开成 [ = "hello" ]，test 看到的是单目运算符 =
x=""
[ $x = "hello" ]       # bash: [: =: unary operator expected

# ✅ 正确：加引号后展开成 [ "" = "hello" ]，合法的字符串比较
[ "$x" = "hello" ]

# ✅ 更好的做法：用 [[，根本不需要引号保护
[[ $x = "hello" ]]
```

**这就是开头场景那个报警的根因。** `[` 是普通命令——shell 先把 `$STATUS` 展开成空串，然后 `[` 看到的就是 `[ = "ready" ]`，它以为 `=` 是一个单目运算符（类似 `-z`），当然报错。

**雷三：`[ ]` 中的 `-a` / `-o` 没有短路求值**

```bash
# ❌ 危险：即使左边为真，右边仍然会执行
[ 1 -eq 1 -a $(rm -rf /tmp/important) -eq 0 ]
# rm -rf 会执行！不管左边结果如何

# ✅ 安全的做法：在 shell 层面用 && 连接两个 [ ] 命令
[ 1 -eq 1 ] && [ $(check_something) -eq 0 ]
# 两个 [ ] 是独立命令，shell 的 && 保证短路

# ✅ 或者用 [[ ]] 的 &&
[[ 1 -eq 1 && $(check_something) -eq 0 ]]
```

> ⚠️ 注意：`$()` 命令替换在任何情况下都会先于外层命令执行。上面"安全"的真正含义是：`[ cond1 ] && [ cond2 ]` 中，如果 cond1 为假，`[ cond2 ]` 这个命令根本不会被调用——**但如果你把 `$(rm -rf ...)` 写在 `[ ]` 里面，shell 在为 `[ ]` 准备参数时就会展开它**。最安全的做法是不要在条件表达式中内嵌有副作用的 `$()`。

**雷四：`(( ))` 的"真"是"非零"，和 C 语言一致——但和 shell 退出码相反**

```bash
(( 0 )) && echo "true" || echo "false"    # → false（0 在算术里是假）
(( 1 )) && echo "true" || echo "false"    # → true（非零是真）
(( 5 > 3 )) && echo "true" || echo "false" # → true

# ⚠️ 这跟命令退出码的逻辑正好相反！
false && echo "false 退出码=1，但不会打印"
true  && echo "true 退出码=0，会打印"
```

在 shell 中退出码 0 表示成功（真），而在 `(( ))` 的算术世界中，0 表示假，非 0 表示真。**这是把 C 语言的布尔逻辑搬进了 shell。**

## 四、核心能力逐轴拆解

三种括号的能力沿六个轴展开。每个轴回答一个具体问题——搞懂一个轴，就搞懂了一类条件判断。

| 能力轴 | 问题 | [ ] | [[ ]] | (( )) |
|--------|------|:---:|:-----:|:-----:|
| 文件测试 | 文件存在吗？可读吗？ | ✅ | ✅ | — |
| 字符串比较 | 两个字符串相等吗？ | ✅ | ✅（更强） | — |
| 模式匹配 | 匹配通配符/正则吗？ | — | ✅ | — |
| 算术比较 | 数字谁大谁小？ | ✅（-eq 风格） | ✅（两者均可） | ✅（C 风格） |
| 逻辑组合 | 多个条件怎么拼？ | ⚠️（-a/-o 无短路） | ✅（&&/\|\| 短路） | ✅（&&/\|\| 短路） |
| 变量安全 | 空变量会炸吗？ | ⚠️（需引号保护） | ✅（安全） | ✅（安全） |

---

### 轴 1：文件测试——三者的最大交集

> 场景：你要检查配置文件是否存在，不存在就创建一个默认的。

```bash
config="/etc/myapp/config.yaml"

# [ ] 写法（POSIX，任何 shell 都能跑）
if [ ! -f "$config" ]; then
    echo "配置文件不存在，创建默认配置"
    cp /opt/myapp/default-config.yaml "$config"
fi

# [[ ]] 写法（bash 专属，更安全）
if [[ ! -f $config ]]; then
    echo "配置文件不存在，创建默认配置"
    cp /opt/myapp/default-config.yaml "$config"
fi
```

两者都支持的文件测试操作符完全相同：

| 操作符 | 含义 | 操作符 | 含义 |
|--------|------|--------|------|
| `-e` | 存在（任意类型） | `-s` | 存在且非空 |
| `-f` | 存在且是普通文件 | `-r` | 可读 |
| `-d` | 存在且是目录 | `-w` | 可写 |
| `-L` | 存在且是符号链接 | `-x` | 可执行 |
| `-p` | 是命名管道 | `-O` | 属主是当前用户 |
| `-S` | 是 socket | `-G` | 属组是当前用户组 |
| `-b` | 是块设备 | `-N` | 上次读取后被修改过 |

文件比较：

```bash
[ file1 -nt file2 ]    # file1 比 file2 新（mtime）
[ file1 -ot file2 ]    # file1 比 file2 旧
[ file1 -ef file2 ]    # 同一个文件（硬链接 / same inode）
```

> ⚠️ `-a` 在文件测试中表示"文件存在"（已废弃，用 `-e` 代替），在逻辑组合中表示"AND"。同一个字母在不同上下文含义完全不同。**建议永远不用 `-a` 做文件测试，只用 `-e`。**

---

### 轴 2：字符串比较——`[ ]` 和 `[[ ]]` 的鸿沟

> 场景：判断用户输入的环境名是否合法。

```bash
env_name="production"

# [ ] 写法：必须给变量加引号，必须用单个 =
if [ "$env_name" = "production" ]; then
    echo "切换至生产环境——请确认操作"
fi

# [[ ]] 写法：不必加引号，= 和 == 等价
if [[ $env_name == "production" ]]; then
    echo "切换至生产环境——请确认操作"
fi
```

字符串操作符对比：

| 操作 | `[ ]` | `[[ ]]` |
|------|-------|---------|
| 相等 | `"$a" = "$b"` | `$a == $b` 或 `$a = $b` |
| 不等 | `"$a" != "$b"` | `$a != $b` |
| 字典序小于 | `"$a" \< "$b"`（必须转义 `<`） | `$a < $b`（不需要转义） |
| 字典序大于 | `"$a" \> "$b"`（必须转义 `>`） | `$a > $b`（不需要转义） |
| 非空 | `-n "$a"` | `-n $a` |
| 为空 | `-z "$a"` | `-z $a` |
| 空变量安全 | ❌ 必须加引号 | ✅ 不需要引号 |

> 💡 为什么 `[ ]` 里 `<` 和 `>` 需要转义？因为它们也是 shell 的重定向符号。`[ "$a" > "$b" ]` 会被 shell 解释为：把 `[` 命令的输出重定向到文件 `$b`。转义后 `\>` 才作为普通字符传给 `test`。

---

### 轴 3：模式匹配——`[[ ]]` 的杀手级能力

> 场景：校验用户输入的版本号格式（如 `v1.2.3`），匹配成功才继续。

```bash
version="v1.2.3"

# 通配符模式匹配（== 在 [[ ]] 中自动启用 glob）
if [[ $version == v[0-9].[0-9].[0-9] ]]; then
    echo "版本号格式正确"
fi

# 正则表达式匹配（=~ 运算符）
if [[ $version =~ ^v[0-9]+\.[0-9]+\.[0-9]+$ ]]; then
    echo "版本号格式正确"
fi

# BASH_REMATCH 捕获分组
if [[ "2024-01-15" =~ ([0-9]{4})-([0-9]{2})-([0-9]{2}) ]]; then
    echo "年: ${BASH_REMATCH[1]}"  # 2024
    echo "月: ${BASH_REMATCH[2]}"  # 01
    echo "日: ${BASH_REMATCH[3]}"  # 15
fi
```

> ⚠️ **`[[ ]]` 中 `==` 的右操作数是 glob 模式，不是正则！** 这是无数人踩过的坑。`[[ abc.txt == *.txt ]]` 匹配成功是因为 `*.txt` 是通配符（glob），不是正则表达式。要用正则表达式，必须用 `=~` 运算符。

> ⚠️ `=~` 右侧不要加引号——加了引号会变成字面字符串匹配，正则特性失效。
>
> ```bash
> [[ "abc123" =~ ^[a-z]+[0-9]+$ ]]     # ✅ 正则匹配：true
> [[ "abc123" =~ "^[a-z]+[0-9]+$" ]]   # ❌ 引号把正则变成了字面字符串
> ```

### 轴 4：算术比较——三种写法三个世界

> 场景：检查当前打开的 fd 数量，超过阈值就告警。

这是最乱的地方——三种括号都能比数字，但语法不同：

```bash
fd_count=512
limit=1024

# [ ] 写法：使用专用的算术操作符（-eq, -ne, -lt, -le, -gt, -ge）
if [ "$fd_count" -gt "$limit" ]; then
    echo "告警：fd 数量超限"
fi

# [[ ]] 写法：两种都能用——可以用 -gt 也可以用 >
if [[ $fd_count -gt $limit ]]; then
    echo "告警：fd 数量超限"
fi
# 或者
if [[ $fd_count > $limit ]]; then
    echo "告警：fd 数量超限"
fi

# (( )) 写法：C 语言风格，最直观
if (( fd_count > limit )); then
    echo "告警：fd 数量超限"
fi
```

`(( ))` 支持全套 C 语言算术运算符：`+` `-` `*` `/` `%` `**` `++` `--` `+=` `<<` `>>` `&` `|` `&&` `||` `!` `~` `^` `? :`。

```bash
# 在 (( )) 中你可以写任意算术表达式
(( count++ ))                # 自增
(( total += price * qty ))   # 累加
(( mask = (1 << 4) | 0x03 )) # 位运算

# 甚至在 for 循环中
for (( i = 0; i < 10; i++ )); do
    echo "迭代 $i"
done
```

> 💡 一条实用原则：**纯数字比较用 `(( ))`；字符串/文件相关用 `[[ ]]`；写 POSIX 兼容脚本用 `[ ]`。** 这样心智负担最小。

### 轴 5：逻辑组合——短路的危险

> 场景：检查一个路径既是目录又可以写入。

```bash
path="/var/log/myapp"

# [ ] 写法：用 -a（AND）和 -o（OR），无短路求值
if [ -d "$path" -a -w "$path" ]; then
    echo "目录存在且可写"
fi

# [[ ]] 写法：用 && 和 ||，有短路求值
if [[ -d $path && -w $path ]]; then
    echo "目录存在且可写"
fi

# 也可以把条件拆开，用 shell 的 && / || 连接多条命令
[ -d "$path" ] && [ -w "$path" ] && echo "目录存在且可写"
```

> ⚠️ `[ ]` 的 `-a` / `-o` **不做短路**——无论左边结果如何，右边都会求值。在复杂条件中这会导致意想不到的执行。**建议：永远不用 `-a` / `-o`。要么用 `[[ && / || ]]`，要么在 shell 层面 `[ cond1 ] && [ cond2 ]`。**

`[[ ]]` 还支持括号分组：

```bash
# 复杂的嵌套条件
if [[ ( -f $config && -r $config ) || ( -d $backup && -w $backup ) ]]; then
    echo "满足部署条件"
fi
```

### 轴 6：变量安全——为什么 `[[ ]]` 几乎总是更好的选择

> 场景：你写了一个函数，接收可选参数。参数可能为空。

这个轴其实隐藏在每一个轴中，但值得单独强调——因为它是从 `[ ]` 迁移到 `[[ ]]` 最核心的理由。

```bash
# 模拟：函数收到空参数
process() {
    local name="$1"

    # [ ] — 如果 name 为空，展开后变成 [ = "admin" ]，语法错误
    # [ "$name" = "admin" ] — 加了引号才安全

    # [[ ]] — 不需要引号，天然安全
    if [[ $name == "admin" ]]; then
        echo "管理员模式"
    fi
}
```

**`[[ ]]` 内部不做单词拆分（word splitting）和文件名展开（pathname expansion）。** 这是它比 `[ ]` 安全的根本原因。

```bash
# 极端案例：变量里包含空格和通配符
filename="my file *.txt"

# [ ] 中不加引号：shell 把 *.txt 展开成当前目录下的所有 .txt 文件
[ $filename = "my file *.txt" ]   # 💥 炸了

# [ ] 中加引号：安全，但必须记住加
[ "$filename" = "my file *.txt" ] # ✅

# [[ ]] 中不加引号：安全，不需要记忆规则
[[ $filename = "my file *.txt" ]] # ✅
```

## 五、组合实战——把条件判断嵌入脚本骨架

三种括号不是独立使用的——它们和 `if`/`while`/`&&`/`||` 组合在一起，构成了 bash 脚本的控制流骨架。

### 经典模式一：防御式编程——先检查再操作

```bash
#!/bin/bash
# 安全的文件操作封装

config_file="/etc/myapp/config.conf"

# 文件存在 → 备份 → 修改
if [[ -f $config_file && -r $config_file ]]; then
    cp "$config_file" "${config_file}.bak.$(date +%Y%m%d)"
    echo "已备份至 ${config_file}.bak.$(date +%Y%m%d)"
else
    echo "错误：配置文件 $config_file 不存在或不可读" >&2
    exit 1
fi
```

### 经典模式二：数值循环——`(( ))` + `while`

```bash
# 重试机制：最多尝试 3 次
retry=0
max_retries=3

while (( retry < max_retries )); do
    if curl -s --fail https://api.example.com/health > /dev/null; then
        echo "服务就绪"
        break
    fi
    (( retry++ ))
    echo "第 $retry 次重试..."
    sleep 2
done

if (( retry >= max_retries )); then
    echo "错误：重试 $max_retries 次后服务仍未就绪" >&2
    exit 1
fi
```

### 经典模式三：正则校验——`[[ =~ ]]` + 分组捕获

```bash
#!/bin/bash
# 解析 Git URL 并提取 owner/repo

parse_git_url() {
    local url="$1"
    # 匹配 git@github.com:owner/repo.git 或 https://github.com/owner/repo.git
    if [[ $url =~ ^(git@|https://)github.com[:/]([^/]+)/([^/.]+)(\.git)?$ ]]; then
        echo "owner=${BASH_REMATCH[2]}"
        echo "repo=${BASH_REMATCH[3]}"
    else
        echo "无法解析的 Git URL: $url" >&2
        return 1
    fi
}

parse_git_url "git@github.com:torvalds/linux.git"
# 输出：owner=torvalds  repo=linux
```

## 六、真实排障全流程复盘

回到开头那个凌晨告警的场景。我们完整走一遍排障流程。

```
初始状态：deploy.sh 第 23 行报错 "unary operator expected"
```

**第一步：定位——哪个条件表达式出了问题？**

```bash
# 在脚本顶部启用调试模式，看 shell 实际执行了什么
bash -x deploy.sh 2>&1 | grep -A2 'STATUS'
```

输出会显示类似 `'[' = 'ready' ']'`——立刻确认是 `$STATUS` 展开为空。

**第二步：确认——为什么变量为空？**

```bash
# 查看 STATUS 的赋值来源
grep -n 'STATUS=' deploy.sh
# 输出：STATUS=$(curl -s https://api.example.com/deploy/status)
```

原来是 API 调用可能返回空。这不是 bug，是真实环境下会出现的情况。

**第三步：修复——选择哪个方案？**

方案 A（最小改动）：给变量加引号 `[ "$STATUS" = "ready" ]`

方案 B（更稳健）：换成 `[[ ]]`，并加默认值兜底

```bash
# 修复后：即使 API 挂了也不会报语法错误
STATUS="${STATUS:-unknown}"
if [[ $STATUS == "ready" ]]; then
    deploy
elif [[ $STATUS == "unknown" ]]; then
    echo "警告：无法获取部署状态，跳过本次部署" >&2
    exit 0
else
    echo "当前状态: $STATUS，等待下次检查"
fi
```

**第四步：验证——覆盖边界条件**

```bash
# 测试空字符串场景
STATUS="" bash -x deploy.sh
# 测试正常场景
STATUS="ready" bash -x deploy.sh
# 测试异常场景
STATUS="blocked" bash -x deploy.sh
```

**第五步：复查——没有引入新问题**

```bash
# 用 shellcheck 做静态检查
shellcheck deploy.sh
# 确保没有 SC2086（未加引号的变量）之类的警告
```

> 整个过程没有靠"感觉"修 bug，而是 `bash -x` 定位 → 分析根因 → 选择修复方案 → 覆盖边界测试 → shellcheck 复查。记住这个流程，比记住任何一个特定的括号写法都重要。

## 七、踩坑清单

- **坑一：`[` 左右缺空格** → 记住 `[` 是**命令名**，不是标点符号。检验方法：`which [` 能看到 `/usr/bin/[`。
- **坑二：`[ ]` 中变量不加引号，且变量为空或含空格** → 养成两个习惯之一：要么永远 `[ "$var" = ... ]` 加引号，要么全面迁移到 `[[ ]]`。
- **坑三：`[ ]` 的 `-a` / `-o` 没有短路** → 永远不用 `-a` / `-o`。要么用 `[[ && / || ]]`，要么在 shell 层面 `[ cond1 ] && [ cond2 ]`。
- **坑四：`==` 在 `[ ]` 中不是 POSIX** → `[ ]` 的字符串相等是 `=`，`==` 是 bash 扩展。要兼容性只用 `=`。
- **坑五：`[[ ]]` 的 `==` 右侧是 glob，不是正则** → 通配符用 `==`，正则用 `=~`。不要搞混。
- **坑六：`=~` 右侧加引号后正则失效** → `[[ $str =~ ^[0-9]+$ ]]` 正确，`[[ $str =~ "^[0-9]+$" ]]` 变成了字面字符串匹配。
- **坑七：`(( ))` 的真假逻辑是 C 语言的，和 shell 退出码相反** → `(( 0 ))` 为假，`(( 1 ))` 为真。这和 `false`（退出码 1）与 `true`（退出码 0）的关系是反的。
- **坑八：`[ ]` 中 `<` 和 `>` 没转义，被当成重定向** → 要么用 `[[ ]]` 省心，要么 `[ "$a" \< "$b" ]` 手动转义。
- **坑九：在 `#!/bin/sh` 脚本里用 `[[ ]]` 或 `(( ))`** → 这两个是 bashism。如果 shebang 是 `#!/bin/sh`，只能用 `[ ]`。检查方法：`ls -l $(which sh)` 看它到底指向谁（在 Ubuntu 上 `sh` 可能是 dash）。

## 八、什么时候用什么——决策速查

| 场景 | 用什么 | 为什么 |
|------|--------|--------|
| 只检查文件是否存在 | `[ -f "$file" ]` 或 `[[ -f $file ]]` | 两者等价，选你习惯的 |
| 字符串比较（可能有空变量） | `[[ $a == $b ]]` | 不怕空变量，不用加引号 |
| 数字比较或运算 | `(( a > b ))` | C 语言语法，最直观 |
| 正则匹配 + 分组捕获 | `[[ =~ ]]` + `BASH_REMATCH` | 唯一选择，其他两种做不到 |
| 通配符匹配 | `[[ == *.txt ]]` | `[ ]` 不支持模式匹配 |
| 需要短路求值的复杂条件 | `[[ ]]` 的 `&&`/`||` | `[ ]` 的 `-a`/`-o` 不短路 |
| POSIX 兼容（`#!/bin/sh`） | `[ ]` | `[[ ]]` 和 `(( ))` 是 bash 专有 |
| 自增/位运算/复合赋值 | `(( ))` | `let` 的天然替代，可读性好太多 |

> 💡 一句话总结：**日常写 bash 脚本用 `[[ ]]` 做条件、`(( ))` 做算术、`[ ]` 只在你需要 POSIX 兼容时出现。**

## 九、换个命令你会了吗？

`[[ ]]`、`(( ))`、`[ ]` 都属于**骨架模式 B**：`条件表达式 → 退出码`。同一模式的命令和结构还有：

- **`test`**：`[ ]` 的别名，`test -f /etc/passwd` 等价于 `[ -f /etc/passwd ]`（不需要 `]`）
- **`let`**：`(( ))` 的前身，`let "a = b + c"` 等价于 `(( a = b + c ))`，但 `(( ))` 可读性碾压
- **`true` / `false`**：直接返回退出码 0/1 的占位命令，`while true; do ... done`
- **`:`**：bash 的 no-op，永远返回 0。`while : ; do ... done` 等价于 `while true; do ... done`

学完这三个括号，你其实已经理解了 bash 脚本里 90% 的条件逻辑骨架。下次遇到奇怪的 `if` 行为，先问三句话：

1. **它用的是哪种括号？**（命令 vs 关键字 vs 算术上下文）
2. **变量展开时有没有单词拆分/路径展开？**（`[ ]` 有，`[[ ]]` 没有）
3. **逻辑组合是否短路？**（`-a`/`-o` 不短路，`&&`/`||` 短路）

三个问题回答完，bug 的根因通常已经浮出水面。

---

> **核心观点：** `[ ]`、`[[ ]]`、`(( ))` 不是三种"写法"，而是三种本质不同的求值机制——**命令**、**关键字**、**算术上下文**。它们的能力边界是固定的，不是"凭感觉加括号"。一旦你理解 `[` 是一个真实存在的命令、`[[` 是 bash 为安全而生的关键字、`((` 是 C 语言算术语法的 shell 版本，你就不再需要猜测"什么时候该用什么"了。
>
