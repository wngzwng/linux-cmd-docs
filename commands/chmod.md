# chmod：从数字权限到符号模式——777 之外的正确选择

> 很多人用了好几年 Linux，chmod 永远只会一种用法——`chmod 777 文件名`，遇到权限问题就一把梭。其实 chmod 是一个精确的权限手术刀，而 777 是把整扇门拆掉——大多数时候你只需要开一扇窗。

## 一、你会遇到的场景

你在服务器上部署了一个 Web 应用，访问时报 403 Forbidden。日志里写着 `Permission denied: /var/www/app/upload/`。

新手的做法：

```bash
# "不就是权限问题嘛，全开就完了"
chmod 777 /var/www/app/ -R
```

几秒钟后网站能访问了——但同时，任何一个能登录这台机器的用户都可以随意修改你的代码。如果 upload 目录里还有用户上传的脚本文件，攻击者甚至可以直接执行。

而真正理解 chmod 的人会先看清楚再动手：

```bash
# 第一步：看看到底缺了什么权限
ls -ld /var/www/app/upload/
# drwxr-xr-x 2 root root ... — 目录属于 root，Web 用户（www-data）根本进不去

# 第二步：精准修复，只改需要改的
chown www-data:www-data /var/www/app/upload/
chmod 755 /var/www/app/upload/      # 或者更精细：750
```

**这就是 chmod 的核心价值：精确控制"谁可以对文件做什么"。** 它不是"解除所有限制"的开关——它是权限手术刀。

## 二、对象模型——Linux 权限世界里有什么

在学参数之前，先把权限模型刻进脑子里。chmod 操作的对象是一个三层结构：

```
文件（或目录）
  │
  ├─ 谁（Who）：分三层
  │   ├─ u = user（所有者）  —— 通常是创建文件的人
  │   ├─ g = group（用户组）  —— 和所有者同组的其他用户
  │   └─ o = others（其他人） —— 既不是所有者也不在同组的用户
  │
  └─ 能做什么（What）：三个基本动作
      ├─ r = read（读）       —— 文件：看内容；目录：列出文件列表
      ├─ w = write（写）      —— 文件：修改内容；目录：增删文件
      └─ x = execute（执行）  —— 文件：作为程序运行；目录：进入目录
```

> 💡 关键认知：**目录的 rwx 含义和文件完全不同。** 目录的 `r` 是"能看目录里有什么文件"（ls），`w` 是"能在目录里创建/删除文件"，`x` 是"能 cd 进这个目录"。一个很常见的困惑：目录是 `rw-` 为什么 cd 不进去？因为你少了 `x`。

再加上三个特殊位，构成完整的权限体系：

```
特殊位（可叠加在基本权限之上）
  ├─ SUID (4000)  —— 可执行文件：运行时以文件所有者的身份执行（如 passwd）
  ├─ SGID (2000)  —— 可执行文件：运行时以文件所属组的身份执行
  │                  目录：目录内新建文件的组继承该目录的组（不是创建者的组）
  └─ Sticky (1000) —— 目录：只有文件所有者才能删除自己的文件（如 /tmp）
```

## 三、语法骨架——先把句型刻进脑子里

```
chmod  [选项]  模式  文件...
       ─┬─    ──┬──  ──┬──
       可选    核心    目标
```

模式有两种写法，解决同一个问题但思路不同：

| 模式 | 句型 | 思维 | 适合 |
|------|------|------|------|
| **数字模式**（八进制） | `chmod 权限值 文件` | "我想要这个文件的最终权限精确是这个值" | 一次性设置全部权限 |
| **符号模式** | `chmod [谁][操作][什么权限] 文件` | "我想给/拿走某些人的某些权限" | 增量修改、加减某个权限 |

属于**骨架模式 C**：`动作 + 目标`。和 kill、systemctl 同族。

⚠️ **在讲具体能力之前，先排一个新手几乎必踩的雷：**

```bash
# ❌ 错误：把 symbolic 模式的 + 当成"设置"
chmod +r file.txt
# 你以为你设了"只读"，实际上 umask 会屏蔽掉 other 的 r——
# 最终可能只有 owner 和 group 加了读权限，others 没有。

# ✅ 正确：明确指定"给谁加"
chmod a+r file.txt     # 所有人加读
chmod u+x script.sh    # 只给所有者加执行

# 或者用数字模式一次性说清楚：
chmod 644 file.txt     # rw-r--r--，没有任何歧义
```

> ⚠️ 符号模式下，**`+` 不加 who 前缀时，行为受 umask 影响**——它不会给被 umask 屏蔽的位加权限。这一点连很多老手都不知道。

## 四、核心能力逐轴拆解

chmod 的能力沿 5 个轴展开。不要背参数——每个轴回答一个具体问题。

| 能力轴 | 问题 | 核心用法 |
|--------|------|---------|
| 数字模式轴 | 最终权限精确是什么？ | 三位/四位八进制数 |
| 符号模式轴 | 想增量修改什么权限？ | `[ugo][+-=][rwxX]` |
| 递归轴 | 目录下所有文件都要改？ | `-R` |
| 特殊位轴 | 需要 SUID/SGID/Sticky？ | `4xxx`/`2xxx`/`1xxx`，或 `u+s`/`g+s`/`+t` |
| 参考轴 | 想让 A 的权限和 B 一样？ | `--reference=参考文件`（GNU 扩展） |

---

### 轴 1：数字模式——"我想要 rw-r--r--"

> 场景：你刚创建了一个脚本，希望自己可读写执行，别人只能读和执行。

```bash
# 逻辑：owner=rwx(7), group=rx(5), others=rx(5)
chmod 755 script.sh
# 结果：-rwxr-xr-x
```

数字模式的记忆法：把每一位看作三位二进制。

```
r=4  w=2  x=1
───  ───  ───
读   写   执行

7 = 4+2+1 = rwx
6 = 4+2+0 = rw-
5 = 4+0+1 = r-x
4 = 4+0+0 = r--
0 = 0+0+0 = ---
```

三个数字分别对应 u/g/o。所以 `chmod 751` = `rwxr-x--x`：owner 全能，group 可读可执行，others 只能执行。

常用组合（值得记住）：

| 数字 | 权限串 | 典型用途 |
|------|--------|---------|
| `644` | rw-r--r-- | 普通文件：我可写，别人可读 |
| `755` | rwxr-xr-x | 脚本/二进制/目录：我可执行，别人也可执行 |
| `600` | rw------- | 私密文件（SSH 私钥要求必须是 600） |
| `700` | rwx------ | 私人脚本/目录：只有我能碰 |
| `750` | rwxr-x--- | 同组协作：我和组员能用，外人不行 |

> 💡 **`chmod 777` 不是"万能钥匙"，而是"我已经放弃了权限控制"的信号。** 永远先想清楚：真的需要"所有人"都能写吗？大多数情况下 755 或 750 就够了。

---

### 轴 2：符号模式——"我只想给组里的人加上写权限"

> 场景：你有一个项目目录，owner 是你自己，现在想让同组的人也能编辑里面的文件。

```bash
# 给 group 加上写权限，不改动 owner 和 others
chmod g+w project/
```

符号模式的三要素组合：

```
谁？         操作？       什么权限？
u(user)      + (加)       r (读)
g(group)     - (减)       w (写)
o(others)    = (设为)     x (执行)
a(all=ugo)                X (条件执行：目录或已有 x 的文件才加)
                          s (SUID/SGID)
                          t (sticky)
```

实用组合：

```bash
chmod u+x script.sh       # 给 owner 加执行权限（最常用）
chmod go-w file.txt       # 拿走 group 和 others 的写权限
chmod a+r file.txt        # 所有人都能读
chmod go=                 # 清空 group 和 others 的全部权限
chmod +X *                # 给目录和已有执行权的文件加执行（安全的"加 x"）
```

> ⚠️ **`X`（大写）是符号模式里最被低估的特性。** `chmod -R +X` 只给目录加 x（目录需要 x 才能进入），不会给普通文件加 x，比 `chmod -R +x` 安全得多。

---

### 轴 3：递归——"整个目录树都要改"

> 场景：你把一个项目目录从别处拷过来，里面所有文件和子目录的权限都需要统一调整。

```bash
# ⚠️ 第一步：先看看当前是什么样
ls -lR project/ | head -40

# 第二步：确认无误后再执行
chmod -R 755 project/
```

> ⚠️ **递归修改是权限误操作的重灾区。** 文件和目录的理想权限通常不同：目录需要 `x` 才能进入，普通文件不需要。一键 `chmod -R 755` 会让所有普通文件也变得可执行——这既不安全也不干净。

更精细的做法：用 find 区分文件和目录分别设权：

```bash
# 目录设 755（需要 x），文件设 644（不需要 x）
find project/ -type d -exec chmod 755 {} \;
find project/ -type f -exec chmod 644 {} \;
```

> 💡 `-R` 的 `-H/-L/-P` 选项控制对符号链接的处理，macOS 上默认不跟随符号链接，Linux (GNU) 也是。绝大多数场景不需要动这些选项——但要知道符号链接本身的权限在 Linux 上不可修改（始终是 `lrwxrwxrwx`，由内核决定）。

---

### 轴 4：特殊位——SUID、SGID、Sticky Bit

> 场景：你需要搞清楚为什么普通用户可以改密码（/usr/bin/passwd），以及 /tmp 目录为什么谁都可以写但删不了别人的文件。

```bash
# 看 /usr/bin/passwd 的权限
ls -l /usr/bin/passwd
# -rwsr-xr-x  — owner 的 x 位变成了 s，这就是 SUID
```

三个特殊位：

```
SUID (4xxx 或 u+s)：可执行文件以文件所有者的身份运行
    └─ 典型：/usr/bin/passwd 的 owner 是 root，SUID 让普通用户临时获得 root 权限来改密码

SGID (2xxx 或 g+s)：可执行文件以文件所属组的身份运行
    └─ 目录：目录内新建文件的组继承该目录的组（协作场景神器）

Sticky (1xxx 或 +t)：目录内只有文件所有者能删除自己的文件
    └─ 典型：/tmp（drwxrwxrwt），大家都能写但互删不了
```

实操示例：

```bash
# 创建一个协作目录：同组的人都能写，新建文件自动继承目录组
mkdir /shared/project
chown :dev-team /shared/project
chmod 2770 /shared/project     # 2=SGID, 770=rwxrwx---

# 验证：ls -ld /shared/project
# drwxrws--- — group 的 x 位变成了 s
```

> ⚠️ **SUID 是可执行安全里最危险的东西。** 一个带 SUID root 的程序如果有漏洞，攻击者就能提权到 root。绝对不要给来路不明的二进制或自己写的脚本设 SUID（Linux 上脚本的 SUID 通常被内核忽略，这是安全设计）。

---

### 轴 5：参考模式——"让 A 的权限和 B 完全一样"

> 场景：你有一个权限设好的参考文件，想让其他文件全部照抄它的权限。
> 💡 `--reference` 是 GNU coreutils 扩展，Linux 上可用，macOS BSD chmod 不支持。

```bash
chmod --reference=template.txt newfile.txt
```

这在批量操作中极其有用——先手工设好一个文件的权限作为黄金标准，然后批量复制。

```bash
# 批量让目录下所有 .sh 文件权限和 deploy.sh 一样
for f in *.sh; do chmod --reference=deploy.sh "$f"; done
```

> 💡 `--reference` 只复制权限位，不改变所有者（那是 chown 的事）。

## 五、真实排障全流程复盘

> 场景：用户反馈网站上传功能报 403，upload 目录存在但写不进去。

```
第一步：定位 → 看目录权限和所有者
──────────────────────────────────
$ ls -ld /var/www/app/upload/
drwxr-xr-x 2 root root 4096 Jun 15 10:00 /var/www/app/upload/
                                    ↑ 目录属于 root
            ↑ others 没有 w 权限

$ ps aux | grep nginx
www-data  1234  ... nginx: worker process
           ↑ nginx 以 www-data 身份运行

结论：nginx 以 www-data 运行，但 upload 属于 root:root，others(r-x) 没有写权限。
      www-data 既不是 owner 也不是 group，被归为 others——所以写不进去。

第二步：确认 → 需要什么权限？
──────────────────────────────────
方案 A：改所有者（推荐）→ chown www-data:www-data /var/www/app/upload/
方案 B：不改所有者，放开 others 写（不推荐，太宽）→ chmod o+w

第三步：预览 → 先看看影响范围
──────────────────────────────────
$ ls -l /var/www/app/ | grep upload
drwxr-xr-x 2 root root 4096 Jun 15 10:00 upload
# 只有一个 upload 目录需要改

第四步：执行 → 精准修正
──────────────────────────────────
$ chown www-data:www-data /var/www/app/upload/
$ chmod 755 /var/www/app/upload/
# 结果：drwxr-xr-x 2 www-data www-data ... upload/

第五步：复查 → 验证修复
──────────────────────────────────
$ sudo -u www-data touch /var/www/app/upload/test.txt && echo "OK"
OK
$ rm /var/www/app/upload/test.txt
```

> 整个过程没有 `chmod 777`，没有 `-R` 炸弹。每一步都知道自己在干什么。

## 六、踩坑清单

- **坑一：`chmod 777` 是条件反射** → 永远先 `ls -l` 看清楚当前权限和所有者。777 不是"解决权限问题"，是"放弃权限控制"。绝大多数场景 755/750/644 就够。

- **坑二：`chmod -R` 不给目录和文件做区分** → `chmod -R 755` 会让文本文件也带上执行位。正确做法：分别对目录和文件设权，或者用 `chmod -R u=rwX,go=rX`（大写 X 只给目录加 x）。

- **坑三：不理解目录 rwx 的含义** → `r`=能 ls，`w`=能增删文件，`x`=能 cd。目录 `rw-` 会让你能列文件但不能进去——因为缺了 `x`。这个坑几乎每个新手都会踩。

- **坑四：给脚本设 SUID** → Linux 上脚本的 SUID 通常被内核忽略（安全机制）。即使某些配置下生效，给脚本来 SUID root 也是灾难性的——攻击者可以通过环境变量注入、符号链接竞争等任意方式提权。

- **坑五：在符号链接上设权限** → Linux 上符号链接的权限始终是 `lrwxrwxrwx`，无法修改。`chmod` 默认作用于链接指向的目标文件。macOS 上用 `-h` 可以改链接自身的权限，但实际效果有限（macOS 检查的是目标文件权限）。

- **坑六：忘了 umask 的存在** → 即使你 `chmod 777` 了一个目录，在它里面新建的文件权限仍然受 umask 控制（默认 umask 022 会让新文件变成 755 目录 / 644 文件）。chmod 改的是已有文件的权限，umask 控制的是新建文件的默认权限——这是两个层面的事。

## 七、什么时候该换工具

| 场景 | 用什么 | 为什么 |
|------|--------|--------|
| 改文件所有者 | `chown` | chmod 只管权限位，不管所有权 |
| 同时改所有者和组 | `chown user:group` | 一个命令搞定，不需要 chown + chgrp |
| 批量修改默认权限 | `umask` | chmod 改已有文件，umask 控制新建文件的默认权限 |
| 更细粒度的权限控制 | `setfacl` / `getfacl` | ACL 可以给多个不同用户分别设不同权限，超越 u/g/o 三层 |
| SELinux 相关权限问题 | `chcon` / `restorecon` | ls -l 看到的是传统权限，`ls -Z` 才能看到 SELinux 上下文 |
| 文件属性（不可变、只追加） | `chattr` / `lsattr` | `chattr +i` 让 root 都无法修改——这是另一层保护 |

## 八、换个命令你会了吗？

chmod 属于**骨架模式 C**：`动作 + 目标`。同一模式的命令还有：

- **chown**：改文件所有者，句型完全一致：`chown 用户:组 文件`
- **kill**：发信号给进程，句型完全一致：`kill -信号 PID`
- **systemctl**：管理 systemd 单元，句型完全一致：`systemctl 动作 单元名`

学完 chmod，你其实已经掌握了这一类命令的"语法"：一个动词（要干什么）+ 一个名词（对谁干）。下次遇到新命令，先问：它是不是也遵循"动作 + 目标"这个骨架？

---

> **核心观点：** 学 chmod 不是为了记住 `777`、`755`、`644` 几个数字，而是理解 Linux 的**三层权限模型**（u/g/o × r/w/x）和**两个操作范式**（数字模式是"设为目标"，符号模式是"增量修改"）。一旦这两个立住了，你就能在任何权限场景下精确地"只改需要改的"，而不是一把梭。权限管理的最高境界不是"让它能跑"，而是"只给它刚好够用的权限"。
>
