
# uptime：一行输出，三个时间维度——你会看吗？

如果你问"服务器现在负载高吗"，`uptime` 一行就够了。它告诉你三件事：**跑了多久、几个人登录、负载是多少。**

但 "负载"（load average）这三个数字，很多人只会看第一个——或者三个都不会看。本文讲清这个被严重误读的指标。

---

## 场景引入：CPU 没满但负载很高

```bash
uptime
# 14:30:00 up 120 days,  2 users,  load average: 8.50, 7.20, 5.10
```

你用 `top` 看了一下，CPU 使用率才 20%。但负载是 8.5——在 4 核机器上这已经超了。

为什么 CPU 没满但负载高？**因为负载统计的不只是 CPU，还包括等待 IO 的进程。** 磁盘 IO 阻塞了大量进程，它们不占 CPU，但被计入负载。

---

## 核心概念：负载的三个数字分别是什么

```bash
uptime
# 14:30:00 up 120 days,  2 users,  load average: 1.20, 0.90, 0.60
#                                  1 分钟负载 ↑   5 分钟 ↑   15 分钟 ↑
```

负载值表示的是：**在对应时间段内，平均有多少个任务正在使用或等待 CPU。**

它不是百分比，而是一个"排队人数"。1.0 意味着平均有 1 个进程在排队，2.0 意味着 2 个，以此类推。

**如何判断负载是否高？**

| 单核 | 4 核 | 含义 |
|------|------|------|
| < 1.0 | < 4.0 | 正常，系统有空闲 |
| ≈ 1.0 | ≈ 4.0 | 刚好满负荷 |
| > 1.0 | > 4.0 | **有进程在排队——负载过高** |

> 💡 核数查看：`nproc` 或 `lscpu | grep '^CPU(s)'`。

---

## 三段时间的含义（趋势分析）

```bash
load average: 8.50, 7.20, 5.10
#             1min  5min  15min
```

三种模式：

| 模式 | 1min vs 15min | 含义 |
|------|--------------|------|
| 上升 | 1min 明显 > 15min | 负载正在爬升——正在出问题 |
| 下降 | 1min 明显 < 15min | 高峰已过，正在恢复 |
| 平稳 | 三者差不多 | 负载稳定——问题已持续一段时间 |

> 💡 **看负载最重要的不是绝对值，是趋势。** `1min: 8 / 5min: 7 / 15min: 5` → 负载正在快速上升，动手排查。`1min: 2 / 5min: 7 / 15min: 8` → 高峰已过，正在恢复，可以不用急。

## 场景驱动

### 1. 接到告警：服务器响应慢

```bash
uptime
# load average: 12.00, 11.50, 10.00
# 负载很高且呈上升趋势（12 > 11.5 > 10）
# → 立刻排查：top / iostat / ps aux
```

### 2. 确认系统已恢复

```bash
uptime
# load average: 0.80, 2.50, 6.00
# 1min 负载降到了 0.80，说明当前压力已解除
# 15min 还有 6.0 是因为它还在"拖着"之前高峰的平均值
# → 系统已恢复
```

### 3. 判断服务器在线了多久

```bash
uptime
# up 120 days
# 上次重启是 4 个月前——说明系统挺稳定（或安全补丁该打了）
```

---

## 新手踩坑总结

- **坑一：把负载当成 CPU 使用率。** 负载 = 排队人数，CPU 使用率 = 百分比。负载高但 CPU 低 → 可能是 IO 阻塞。
- **坑二：不看核数直接比数字。** 负载 4.0 在 1 核机器上是灾难，在 8 核机器上轻轻松松。
- **坑三：只看第一个数字。** 三个数字的趋势比单个值重要得多。
- **坑四：用 uptime 替代监控系统。** uptime 是快照，不是历史趋势。生产环境还是要 Prometheus / Zabbix 等。

---

## 最后

uptime 只有一行输出，但它回答的是运维的三个基本问题：机器跑了多久（稳定性）、几个人在上面（当前活动）、系统忙不忙（负载趋势）。

下次看到 `load average` 里的三个数字，别只看第一个——看看它们之间的关系。趋势比绝对值更能告诉你现在发生了什么。
