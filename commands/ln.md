# ln：软链接和硬链接——理解 Linux 文件系统的第一道门

> 很多人用了好几年 Linux，从来没搞清楚硬链接和符号链接的区别。`ln -s` 就是"快捷方式"？不完全是。理解了 ln，你才算真正理解了"Linux 里文件名是什么"。

## 一、你会遇到的场景

某天你把一个 10GB 的文件"复制"了一份到另一个目录——磁盘使用翻了一倍。其实你不需要复制——硬链接可以让同一个文件数据块有两个名字，不占额外空间。

又或者你升级了一个库文件（`libfoo.so.1 → libfoo.so.2`），程序立刻挂了——因为符号链接的链条断了。

**这就是 ln 的核心价值：创建文件的链接——硬链接是同一个数据的另一个名字，符号链接是指向路径的指针。**

## 二、硬链接 vs 符号链接——一张表说清楚

```
硬链接 (hard link)                    符号链接 (symbolic link / symlink)
─────────────────────────────         ─────────────────────────────
直接指向 inode（数据块）              指向路径字符串（不是 inode）
同一文件系统内                          可以跨文件系统
删了"原文件"链接仍有效                 删了原文件链接就断了（悬空链接）
不能链接目录（通常）                    可以链接目录
ls -l 看不出谁是"原文件"               ls -l 显示 -> 目标
共享同一个 inode 号                     不同 inode
                                      
验证：ls -li file1 file2              验证：ls -l symlink
# inode 号相同，link count = 2         # 看到 -> target
```

> ⚠️ **"硬链接是复制"是 Linux 新手最常见的误解之一。** 硬链接不是复制——它和原文件指向的是磁盘上同一个 inode。修改硬链接的内容，原文件的内容也变了（因为它们根本就是同一个数据块）。删除"原文件"不会让硬链接失效——数据还在，只是 inode 的引用计数减了 1。

## 三、语法骨架

```
ln  [选项]  源  目标
    ──┬──   ─┬   ─┬
     哪种链接 从哪   到哪
```

## 四、核心能力逐轴拆解

| 能力轴 | 问题 | 选项 |
|--------|------|------|
| 类型轴 | 硬链接还是符号链接？ | 默认(硬链接)、`-s`(符号链接) |
| 覆盖轴 | 目标已存在怎么办？ | `-f`(覆盖)、`-i`(询问)、`-n`(不跟随目标符号链接) |
| 反馈轴 | 告诉我做了什么？ | `-v`(详细输出) |

---

### 轴 1：类型轴——"硬链接还是符号链接？"

```bash
# 硬链接（默认）：同一个 inode，不同文件名
ln original.txt hardlink.txt

# 符号链接 -s：指向路径的指针
ln -s /usr/local/bin/python3 python
# → python -> /usr/local/bin/python3

# 符号链接到目录
ln -s /var/log logs
# → logs -> /var/log
```

```bash
# 如何判断：查看 inode 号和链接计数
ls -li original.txt hardlink.txt
# 一样的 inode 号 → 硬链接
# link count = 2 → 两个文件名指向同一个 inode

ls -l python
# lrwxr-xr-x ... python -> /usr/local/bin/python3
# 第一个字符是 l → 符号链接
```

> 💡 判断原则：**想省磁盘空间、同一文件系统内 → 硬链接。需要跨文件系统、链接目录、清楚看到链接关系 → 符号链接。** 90% 的日常场景用符号链接就够了。

---

### 轴 2：覆盖轴——"目标已存在怎么办？"

```bash
# -f：强制覆盖（先删除已有目标再创建链接）
ln -sf /new/path/python python   # 覆盖已有的符号链接

# -n：不跟随已有符号链接（把符号链接本身替换掉，而非它指向的目标）
ln -sfn /new/path/dir dir_link
```

> ⚠️ **`ln -sf /new/path symlink` 的行为依赖 `symlink` 是否指向目录。** 如果 `symlink` 已存在且指向一个目录，`ln -sf` 会在目录内部创建链接而不是替换 `symlink` 本身。加 `-n` 解决这个问题：`ln -sfn`。

---

### 轴 3：反馈轴

```bash
# -v：打印每个创建的链接
ln -sv /usr/local/bin/* /usr/bin/
```

## 五、实用场景

### 场景 1：版本管理——用符号链接实现"当前版本"指针

```bash
# 部署应用的新版本
cp -r app-v1.2.0/ /opt/app-v1.2.0/
ln -sfn /opt/app-v1.2.0 /opt/app-current
# nginx 配置指向 /opt/app-current → 升级只需重做链接
```

### 场景 2：配置文件管理（dotfiles）

```bash
ln -s ~/dotfiles/.bashrc ~/.bashrc
ln -s ~/dotfiles/.vimrc ~/.vimrc
# 所有配置文件在一个 git 仓库里，链接到原位
```

### 场景 3：节省磁盘——大文件的硬链接

```bash
# 同一文件系统的两个目录共享数据
ln /data/raw/dataset.tar /data/backup/dataset.tar
# 不占额外空间，删除任一方不影响另一方（只要还有硬链接数据就在）
```

## 六、踩坑清单

- **坑一：硬链接不能跨文件系统** → `ln /mnt/usb/file.txt ~/` 会报 `Invalid cross-device link`。跨文件系统用 `ln -s`。
- **坑二：`ln -sf` 目标是指向目录的符号链接时，行为诡异** → 加 `-n`：`ln -sfn`。
- **坑三：符号链接断了（dangling symlink）不会自动报错** → `ls -l` 能看到红色/闪烁的断链提示，但访问它时才报 "No such file"。定期检查：`find /path -type l ! -exec test -e {} \; -print`。
- **坑四：硬链接的同 inode 性质意味着不能有"备份"的错觉** → 修改硬链接等于修改原文件。需要真正的复制用 `cp`。
- **坑五：`ln` 默认行为是硬链接，不是符号链接** → 忘记加 `-s` 会创建硬链接而不是符号链接——去 `ls -l` 确认。

## 七、什么时候该换工具

| 场景 | 用什么 | 为什么 |
|------|--------|--------|
| 创建文件/目录的别名 | ln | ln 就是干这个的 |
| 真正的文件复制 | `cp` | ln 不复制数据块 |
| 批量管理符号链接 | `stow` / `dotbot` | 管理 dotfiles 的大型链接集合更方便 |
| 找断掉的符号链接 | `find -type l ! -exec test -e {} \; -print` | ln 本身不检查有效性 |

---

> **核心观点：** 学 ln 不是为了记住 `-s -f -n` 三个选项——而是理解 **硬链接 = 同一个 inode 的另一个名字，符号链接 = 指向路径的指针**。这一句话就是 Linux 文件系统的灵魂。
