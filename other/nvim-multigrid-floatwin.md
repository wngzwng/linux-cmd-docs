## 一、浮动窗口：`popup_create()` vs `nvim_open_win()`

Neovim 世界里存在两个创建"浮动窗口"的 API，它们背后代表了两种完全不同的架构思路。

### 1.1 `popup_create()` — Vim 8.2+ 的单网格补丁

这是 Bram Moolenaar 在 Vim 8.2 中引入的原生特性，Neovim 出于兼容目的也实现了它。

**本质**：在单网格（single-grid）模型上"贴"一个浮动层。它不改变窗口布局树，只是在渲染时叠在已有内容之上。

**技术特征**：

- 定位通过 `textprop`（文本属性）或绝对行列号计算，但它的几何信息**不在多网格事件中暴露**
- 外部 UI 无法区分它和普通窗口——GUI 前端要么看不见，要么只能看到一块"突变区域"
- 无法和 split 窗口做平滑的锚定（anchor）、相对移动
- 没有 `win_config` 的完整配置能力：border、title、footer 等受限
- 生命周期管理弱：关闭时可能残影，嵌套 popup 行为不统一

**设计哲学**：一个"够了就行"的轻量弹窗，为 Vim 的单网格世界而生。

### 1.2 `nvim_open_win()` — Neovim 原生多网格一等公民

Neovim 从 API v5 开始提供，v6 完善的**原生浮动窗口 API**。

**本质**：在多网格架构中创建一个**独立的 grid**。浮动窗口在 grid 层面和普通 split 窗口**完全平权**——只不过它的 grid 可以浮动、重叠、设置 z-index。

**完整能力清单**：

| 特性 | 说明 |
|---|---|
| `relative='editor'\|'cursor'\|'win'` | 三种锚定模式：相对编辑器、相对光标、相对另一窗口 |
| `anchor` + `row`/`col` | 精确像素级或行列级定位 |
| `border` | 支持 `'none'` / `'single'` / `'double'` / `'rounded'` / `'solid'` / `'shadow'`，以及自定义字符列表 |
| `title` / `title_pos` | 浮动窗口标题及位置控制 |
| `footer` / `footer_pos` | 浮动窗口底部信息及位置控制 |
| `zindex` | 精确控制堆叠顺序 |
| `noautocmd` | 精细控制事件触发，避免副作用风暴 |
| `style='minimal'` | 禁用内置 UI 元素，适合插件自绘 |

**外部 UI 友好**：每个 float win 通过 `win_viewport` / `grid_resize` / `grid_line` / `win_pos` 等事件独立发出渲染数据，GUI 前端可以把它当成一个独立的可拖动"面板"来处理。

**设计哲学**：浮动窗口是多网格架构的一等公民，不是后贴的补丁。

### 1.3 对比速查表

| 维度 | `popup_create()` | `nvim_open_win()` |
|---|---|---|
| 所属架构 | 单网格（single-grid） | 多网格（multigrid） |
| 窗口在布局树中的位置 | 不存在于布局树，渲染时叠上 | 独立 grid，与 split 窗口平权 |
| 外部 UI 感知 | 无法区分，GUI 前端难以处理 | 完整事件流，前端可以独立渲染 |
| 锚定能力 | 仅行列绝对坐标 | cursor / editor / win 三种相对锚定 |
| 边框/标题/脚注 | 有限 | 完整支持 |
| 嵌套行为 | 不统一 | 行为明确，事件完整 |
| z-index 控制 | 无 | `zindex` 精确控制 |
| 适用场景 | Vim 兼容、简单弹窗 | 插件 UI、外部 GUI、复杂布局 |

## 二、多网格（multigrid）架构详解

### 2.1 什么是多网格

传统的 Vim/Neovim 把整个 TUI 屏幕视为一块**单一画布**。所有的窗口、状态栏、命令行、消息、弹出菜单都在这块画布上"画格线"——你看到的分割线只是画上去的字符，不是真正的独立区域。

**多网格架构**把这个单一画布拆解为多个独立的、可单独刷新的 **grid（网格）**。

```
┌─────────────────────────────────────────────┐
│  默认 grid (global grid，id=1)               │
│                                             │
│  ┌─────────────────┐  ┌──────────────────┐  │
│  │ 窗口 A 的 grid   │  │ 窗口 B 的 grid    │  │
│  │ (grid id=2)     │  │ (grid id=3)      │  │
│  │                 │  │                  │  │
│  └─────────────────┘  └──────────────────┘  │
│                                             │
│  ┌──────────────────────────────┐           │
│  │ 浮动窗口 1 (grid id=4, z=50) │           │
│  └──────────────────────────────┘           │
│                                             │
│  ┌──────────────────────────────────────┐   │
│  │ 消息/命令行 grid (grid id=5)          │   │
│  └──────────────────────────────────────┘   │
└─────────────────────────────────────────────┘
```

每一个 grid 拥有自己独立的：
- 行列坐标系（width × height）
- 光标位置
- 高亮属性
- 滚动偏移

网格之间通过事件（`win_pos`、`win_viewport` 等）告知彼此在整个编辑器坐标系中的位置和 z-order。

### 2.2 核心概念：grid 的层次结构

```
global grid (id=1) ─── 整个编辑器屏幕的根 grid
  ├── window grid ─── 每个 split 窗口对应一个 grid
  │     ├── 浮动窗口 grid ─── 锚定在某窗口上的浮动窗口
  │     └── 浮动窗口 grid ─── zindex 决定相互遮挡
  ├── message grid ─── `:messages` 区域
  ├── cmdline grid ─── 命令行输入区域
  └── wildmenu grid ─── 通配符补全菜单
```

**关键规则**：

1. **grid 之间相互独立**：A 窗口的内容变化不会触发 B 窗口的 grid 重绘。
2. **z-index 决定叠加**：浮动窗口之间通过 `zindex` 决定谁在上层。
3. **外部 UI 是第一消费者**：所有 grid 事件通过 msgpack-RPC 推送给 UI 前端，前端自行决定如何映射到 OS 原生窗口。

### 2.3 关键事件流

多网格模式下，Neovim 向前端推送的核心事件：

| 事件 | 含义 |
|---|---|
| `grid_resize` | 某个 grid 的尺寸发生了变化 |
| `grid_line` | 某 grid 的某一行内容需要更新 |
| `grid_cursor_goto` | 某个 grid 内的光标移动 |
| `grid_scroll` | 某个 grid 内发生滚动 |
| `grid_destroy` | 某个 grid 已销毁（如浮动窗口关闭） |
| `win_pos` | 某窗口相对于编辑器全局坐标的位置 |
| `win_viewport` | 某窗口在 grid 坐标系内的可见视口 |
| `win_close` | 窗口关闭 |
| `msg_set_pos` | 消息区域的尺寸和位置 |

### 2.4 解决的问题矩阵

| 问题 | 单网格时代的窘境 | 多网格如何解决 |
|---|---|---|
| **外部 GUI 开发** | GUI 前端需要解析整个屏幕的 ANSI/diff，推测"这一段文字属于哪个窗口"，极其脆弱 | 每个 grid 独立推送渲染数据，GUI 前端直接收到"窗口 A 第 3 行变了"的精确通知 |
| **浮动窗口/TUI 组件共存** | popup、autocomplete、hover、cmdline 全挤在一块画布上，互相覆盖、闪烁 | 每个 UI 组件独占一个 grid，独立渲染，互不干扰 |
| **性能** | 任意一个窗口内容变化，整个屏幕重新 diff/重绘 | 只刷新变化的 grid，大幅减少重绘范围和 CPU 开销 |
| **窗口语义识别** | "这一行属于哪个 buffer？哪个窗口？"需要反向解析屏幕坐标 | 事件直接携带 `grid` ID，UI 可维护 grid → window 的一对一映射 |
| **跨窗口 anchor** | 只能用行列坐标硬算，窗口移动后错位 | grid 有独立的几何描述，锚定关系由 Neovim 核心维护并实时推送位置变化 |
| **多显示器/多窗口 OS 布局** | 无法想象——整个编辑器就是一块终端屏幕 | 理论上每个 grid 都可映射到独立的 OS 原生窗口（虽然目前主流前端尚未充分利用） |

**一句话总结**：多网格把"终端字符画布"升级为"语义化的 UI 组件树"，让 Neovim 从一个"终端程序"变成了一个"可以嵌入任意 GUI 的编辑器引擎"。

## 三、同类方案全景对比

这个问题的本质是：**如何在文本编辑器核心和多样化 UI 之间解耦？** 业界有以下几条路线。

### 3.1 终端复用器路线（tmux）

不改变编辑器内部架构，把"窗口管理"外包给外部工具。

**做法**：每个编辑区域是一个独立的 `:terminal` 或 tmux pane，由 tmux 做分割、重叠、布局。

- ✅ 简单，编辑器零改动，和任何 CLI 工具兼容
- ✅ TUI 体验纯粹
- ❌ 编辑器不知道它的"窗口"在哪，语义完全丢失
- ❌ 浮动提示/补全无法跨 pane
- ❌ 每个 pane 独占一个 Neovim 实例（或 `:terminal` 内嵌），资源开销高
- ❌ 复制/粘贴/寄存器不能在 pane 间优雅共享

**代表**：tmux 多 pane + 多个 nvim 实例、`:terminal` + `jobstart()`

### 3.2 GUI 原生路线（传统 IDE 架构）

编辑器内核提供 buffer/文档模型，GUI 层完全负责窗口管理。

**做法**：编辑器核心不关心窗口。GUI（GTK / Cocoa / Qt / Web）用自己的 widget tree 管理窗口、分割、浮动面板。核心只暴露"请渲染这段文本"的 API。

- ✅ 天然支持原生窗口拖动、多显示器、透明/阴影、复杂动画
- ✅ GUI 体验极致
- ❌ TUI 模式需要另起炉灶或严重降级
- ❌ 插件生态割裂——TUI 插件和 GUI 插件各玩各的
- ❌ 快捷键/操作模型容易在 TUI / GUI 间不一致
- ❌ 维护两套渲染路径，核心团队负担重

**代表**：
- **Emacs**：buffer + frame + window 在 C 层有统一抽象，但 GUI / TUI 的渲染路径是分开的
- **Oni2**：核心是 libvim + Revery GUI，TUI 非主要目标
- **IntelliJ / JetBrains**：核心是 Swing/Java，窗口管理是 JVM 原生能力

### 3.3 前后端分离路线（Headless + RPC）

编辑器核心彻底变成 headless 服务，UI 是一个完全独立的进程。

**做法**：核心进程只通过 RPC（msgpack / JSON）暴露编辑操作和渲染事件，UI 进程自己决定如何显示。类似 LSP 把语言智能从编辑器中分离出去的思路。

- ✅ 最大解耦——任何前端（终端 / Web / iOS / VR）都可以对接同一个核心
- ✅ 自然支持远程编辑（核心在服务器，前端在本地）
- ❌ 延迟敏感——每一帧渲染都要经过 IPC
- ❌ 前端承担了太多责任：排版、光标渲染、输入法
- ❌ 极其复杂——目前没有大规模成功的先例
- ❌ 标准难以统一：每个前端都要重新实现大量编辑行为

**代表**：
- **Neovim `--headless` + 外部 UI**：实际上 Neovim 的多网格正是这个路线的折中——核心仍然管理窗口语义，但渲染数据通过标准化事件发送给前端
- **Xi-editor**：Rust 核心 + JSON-RPC 前端（项目已停滞，验证了这条路线的工程难度）

### 3.4 锚定文本属性路线

不改变窗口模型，而是在单网格画布上通过某种标记实现"浮动区域"。

**做法**：在 buffer 中插入虚拟文本/标记，渲染时"挂"在光标或锚点上显示，但不占据实际布局空间。

- ✅ 改动最小，兼容所有现有渲染路径
- ✅ 实现复杂度最低
- ❌ 重叠/遮挡/嵌套完全靠约定，没有真正的 z-order
- ❌ 外部 UI 完全无感——对 GUI 前端是一个黑盒
- ❌ 多个浮动区域同时存在时行为不可预测
- ❌ 无法实现复杂布局（如分栏的浮动面板）

**代表**：
- Vim 的 `textprop` + `popup_create()`（最初就是在这条路线上）
- Neovim 的 `nvim_buf_set_extmark()` 虚拟文本（单网格模式下作为补充）
- Emacs 的 overlay

### 3.5 Web 技术栈路线（VSCode）

以浏览器引擎为渲染层，窗口/浮动由 DOM/CSS 原生管理。

**做法**：编辑器核心（Monaco）运行在 renderer 进程，语言服务运行在独立进程（LSP），UI 是 DOM + CSS 原生。

- ✅ CSS 的 z-index / flex / grid 天然处理所有"浮动"和"布局"问题
- ✅ 跨平台由 Chromium 承担
- ✅ 生态庞大、插件丰富
- ❌ 内存/启动开销大
- ❌ 终端模拟只能嵌套（xterm.js），限制了 TUI 插件的深度
- ❌ 文本渲染不是等宽/字符格级别的精确控制（subpixel 渲染定位）
- ❌ 键盘事件模型和终端工具链差异大

**代表**：VSCode（Monaco Editor + Electron）、Codium、Theia

### 3.6 六条路线综合对比

| 路线 | 窗口语义归谁管 | 浮动/重叠能力 | 外部 UI 友好度 | TUI 兼容性 | 代表 |
|---|---|---|---|---|---|
| 单网格 + popup | 编辑器（但扁平） | 弱 | 差 | ★★★★★ | Vim 8.2+ |
| **多网格（Neovim）** | **编辑器核心** | **强** | **★★★★★** | **★★★★★** | **Neovim ≥0.5** |
| tmux 外包 | tmux | 弱 | 无 | ★★★★★ | tmux + nvim |
| GUI 原生 | GUI toolkit | 超强 | 仅 GUI | ☆ | Emacs GUI, IntelliJ |
| 前后端分离 | 前端 | 取决于前端 | 天然好 | 取决于前端 | Xi-editor, Neovim headless |
| Web 技术栈 | DOM/CSS | 超强 | 天然好 | ★★☆ | VSCode, Monaco |

## 四、设计哲学与总结

Neovim 多网格的精妙之处可以归纳为：

> **它找到了一条同时最大化 TUI 兼容性和外部 UI 友好性的中间路线。**

核心原则：

1. **"语义归核心，渲染归前端"**：Neovim 核心负责"这是什么"（哪个窗口、什么高亮、位置几何），每个前端自己决定"怎么画"。
2. **标准化渲染协议**：`grid_line` / `win_pos` / `grid_resize` 等事件构成了一个精确定义的渲染协议，足以让前端实现复杂交互——浮动窗口拖动、外接窗口、多窗口自由布局。
3. **TUI 零牺牲**：在 tmux 里跑 `nvim`，体验和原来完全一致，因为默认前端的 grid 合并策略（把多个 grid 合并回单网格渲染）处理得天衣无缝。
4. **渐进式架构**：你可以用 `'guicursor'` / `'termguicolors'` 等选项逐步启用多网格特性，不需要一次性迁移。

最终效果：**同一个 Neovim 核心，同一套插件，既能在 tmux 的终端里跑，也能在 macOS 的 native GUI 里跑，还能在 iPad 的 Web 前端里跑——而且浮动窗口、补全菜单、消息提示在每个前端里都有原生级的表现。** 这是目前所有文本编辑器架构方案中，在"统一内核 + 多样前端"这个维度上走得最远的。
