## Layer 0：钩子

### 目的

用一个"反差"制造好奇，让读者愿意继续往下读。

### 写法

标题公式：**"为什么 X 很强，但大多数人一直不会用？"**

变体：
- "X 远比你想象的强大——从只会 `xxx` 到真正驾驭它"
- "用了 X 年 Linux，你可能从没用对过 X"
- "X 命令：90% 的人只用到了它 10% 的能力"

### 反例

```
# ❌ 平淡
find 命令的使用方法

# ❌ 太技术
Linux find 命令参数详解

# ✅ 有反差感
为什么 find 很强，但 90% 的人只会 -name？
```

## Layer 1：场景引入 + 功能认知

### 目的

先摆问题，再给答案。让读者从"我遇到过这个"开始，而不是从"find 命令用于查找文件"开始。

### 结构要素

1. **真实场景**：读者可能遇到过的实际问题（磁盘告警、端口占用、日志找不着）
2. **新手做法**：笨的、慢的、错的做法（制造"我好像也是这样的"共鸣）
3. **正确做法**：一行命令干净解决
4. **反差感**：新手半小时 vs 老手几秒钟
5. **一句话定义**：收尾时点出命令的本质功能

### 示例

```markdown
## 你会遇到的场景

某天你收到磁盘告警：根分区使用率 95%。

新手的第一反应往往是 cd 进各个目录，挨个 du -sh *，一层层往下翻，运气不好的话能翻半小时。

而真正理解 find 的人，只会敲一行：

\```bash
find / -type f -size +100M -exec ls -lh {} \; 2>/dev/null
\```

几秒钟之后，所有大文件列出来，元凶一目了然。

**这就是 find 的核心价值：在文件系统里按任意条件查找文件，并对结果执行操作。**
```

### 反例

```markdown
# ❌ 不要这样开头
find 命令用于在目录树中查找文件。它支持按名称、大小、时间等多种条件进行过滤。
```

## Layer 2：IO 模型图解

### 目的

帮读者建立"数据怎么流动"的心智模型。这一步是所有后续理解的基础。

### 写法

- 用文字流程图（ASCII art 或缩进箭头）
- 不要画得太复杂——3-4 个处理步骤即可
- 关键洞察：**"理解了 IO 模型，很多参数就自然出现了——它们不过是在改变输入来源、处理方式或输出形式"**

### 示例

```markdown
## 它是怎么工作的

find 的本质不是 `command + options`，而是 `文件树 → 遍历 → 过滤 → 动作 → 结果`：

\```
文件系统（从某个目录开始）
    │
    ↓ 递归遍历每一个文件和目录
    │
    ↓ 按条件过滤：名字对吗？大小对吗？时间对吗？
    │
    ↓ 对匹配的文件执行动作（打印/删除/执行命令）
    │
输出：匹配的文件路径列表
\```

> 💡 理解了 IO 模型，-r（递归）、-type（过滤类型）、-print/-delete（动作）这些参数就自然出现了——它们分别控制"去哪找"、"怎么过滤"、"对结果做什么"。
```

## Layer 3：语法骨架 + ⚠️ 排雷

### 目的

给读者一个句型框架，并在他们可能犯错的地方提前预警。

### 结构

1. **句型**：用 `[槽位]` 标记参数位置
2. **分类**：标注属于五种骨架模式（A/B/C/D/E）的哪一种
3. **排雷**：选一个最常见、后果最严重的错误，用 ❌ ✅ 对比
4. **解释**：说明为什么错（Shell 展开机制、默认行为误解等）

### 示例

```markdown
## 语法骨架

\```
find  [从哪里开始]  [按什么条件过滤]  [对结果做什么]
      ──┬──         ──────┬──────     ────┬───
      起点槽              条件槽            动作槽
\```

属于**骨架模式 A**：`源 → 过滤 → 目标`。同一模式的命令还有 rsync——理解了 find 的句型，rsync 的语法也会觉得眼熟。

⚠️ **在讲具体能力之前，先排一个新手几乎必踩的雷：**

\```bash
# ❌ 错误：-exec 忘了分号，语法直接报错
find . -name "*.log" -exec rm {}

# ✅ 正确：\; 是 -exec 的结束标志，必须带
find . -name "*.log" -exec rm {} \;
\```

`-exec` 后面跟的是一个完整的 shell 命令，`{}` 是匹配文件的占位符，`\;` 告诉 find "命令到此结束"。忘了 `\;`，find 不知道你的命令在哪结束，直接报语法错误。
```

### 排雷选题原则

- 选最常见的（80% 新手会踩）
- 选后果严重的（数据丢失、服务中断）
- 纠正一个流传很广的误解最好（如 "ctime 是创建时间"）

## Layer 4：能力轴场景化拆解

### 目的

这是教程的核心——逐轴展开，每个轴配一个微型场景。

**关键原则：能力轴表只是骨架，场景才是血肉。**

### 每个轴的写法

```
### 轴 N：【轴名】——【这个轴回答什么问题】

> 场景：【1-2 句话的微型场景——什么时候你会用到这个轴】

命令示例 + 解释

进阶组合用法（可选）

⚠️ 纠正常见误解（如果有）
```

### 示例

```markdown
### 轴 3：时间轴——"什么时候改的/读的？"

> 场景：你想清理 30 天前的旧日志，但不确定具体文件名。

\```bash
# 找 30 天前修改过的 .log 文件
find /var/log -name "*.log" -mtime +30
\```

关键符号：`+n` 表示"超过 n 天"，`-n` 表示"n 天以内"，`n`（无符号）表示"恰好 n 天前"。

> ⚠️ **ctime 不是"创建时间"！** Linux 文件系统不记录创建时间（大多数情况下）。ctime 是 **inode 变更时间**——权限改了、硬链接数变了、所有者变了都会更新 ctime。真正的"内容修改时间"是 mtime。

\```bash
# 找最近 10 分钟内修改过的文件（适合追踪"刚才干了什么"）
find . -mmin -10

# 配合 -ls 看详细信息
find /var/log -mtime +30 -ls
\```
```

### 常见误解纠正参考

| 命令 | 常见误解 | 正确认知 |
|------|---------|---------|
| find | `-ctime` 是创建时间 | ctime 是 inode 变更时间 |
| ss | 不加 `-n` 更快 | 不加 `-n` 反而更慢（DNS 解析延迟） |
| ss | 看不到进程就是没有 | 非 root 用户看不到其他用户的进程，加 `sudo` |
| lsof | 只能看文件 | 在 Linux 里一切皆文件——socket、pipe 都能看 |
| tar | `-` 在选项前可有可无 | BSD tar 不需要 `-`，GNU tar 可选，但建议加 `-` 保持一致性 |

## Layer 5：Pipeline 组合

### 目的

从单个命令升级到管道组合——这是 Linux 真正强大的地方。

### 结构

1. **管道图**：ASCII art 展示数据流
2. **命令**：完整的管道命令
3. **IO 匹配解释**：这是最关键的部分——解释为什么前一个命令的输出恰好是后一个命令的输入
4. **💡 生产建议**：空格文件名、错误处理等

### 示例

```markdown
## Pipeline 组合

\```
find（找到文件）  →  grep（过滤内容）  →  wc（统计数量）
   输出：路径列表      输入：文件内容      输入：文本行
\```

\```bash
find /var/log -name "*.log" -mtime -7 -print0 | xargs -0 grep "ERROR" | wc -l
\```

> 💡 这里能串起来的关键是：
> - `find -print0` 输出以 `\0` 分隔的文件路径
> - `xargs -0` 接受 `\0` 分隔的路径，传给 grep
> - `grep` 从这些文件里找含 ERROR 的行，输出到 stdout
> - `wc -l` 从 stdin 读行，输出行数
>
> 每一个连接点，IO 格式都是匹配的。这就是为什么理解 IO 模型比记参数更重要。
```

## Layer 6：真实排障全流程复盘

### 目的

回到开头的场景，完整走一遍。这层验证了前面讲的所有知识是可组合的。

### 结构

```
第一步：定位  →  命令 + 解释（用了哪个能力轴，为什么）
第二步：确认  →  命令 + 解释（确认猜想）
第三步：预览  →  dry-run / print（安全习惯！先看看要操作什么）
第四步：执行  →  实际命令
第五步：复查  →  验证结果
```

### 关键原则

- **任何 destructive 操作前先 preview**
- **不是"一步到位"**——要展示中间的思考过程
- **结尾总结**："整个过程没有手动进任何一个目录，全程靠命令的条件组合完成"

### 示例

```markdown
## 真实排障全流程复盘

回到开头的磁盘告警场景：

**第一步：定位——找出所有大于 100MB 的文件**
\```bash
find / -type f -size +100M -exec ls -lh {} \; 2>/dev/null
\```
用了范围轴（`/`）、类型轴（`-type f`）、大小轴（`-size +100M`）、动作轴（`-exec ls -lh`）。`2>/dev/null` 吞掉没有权限访问的目录报错。

**第二步：确认——是不是都在 /var/log 下？**
\```bash
find /var/log -type f -size +10M -ls
\```

**第三步：预览——看看有哪些 30 天前的日志**
\```bash
find /var/log -name "*.log" -mtime +30 -print
\```
⚠️ 在加 `-delete` 前，先用 `-print` 确认。

**第四步：执行——清理**
\```bash
find /var/log -name "*.log" -mtime +30 -delete
\```

**第五步：复查——磁盘回来了吗？**
\```bash
df -h /
\```

> 整个过程没有手动进任何一个目录，全程靠 find 的条件组合完成定位→确认→清理→复查。
```

## Layer 7：踩坑清单 + 工具边界 + 迁移提示

### 目的

收尾，总结所有陷阱，诚实给出工具的边界，帮读者触类旁通。

### 三个子模块

#### 7a. 踩坑清单

列表形式，每条一行。格式：

```
- **坑一：xxx** → 正确做法是 xxx
```

#### 7b. 工具边界：什么时候该换工具

| 场景 | 用什么 | 为什么 |
|------|--------|--------|
| 命令擅长的 | 本命令 | 原因 |
| 命令不擅长的 | 替代工具 | 原因 |

#### 7c. 迁移提示

> X 属于**骨架模式 Y**——`句型`。同一模式的命令还有 A、B、C。学完 X，你其实已经掌握了这一类命令的"语法"。

### 示例

```markdown
## 踩坑清单

- **坑一：ctime 不是创建时间** → 文件修改时间看 mtime
- **坑二：-exec 忘了 \; 直接报错** → \; 是结束标志，必须带
- **坑三：-delete 前不确认** → 先用 -print 列出来看一眼
- **坑四：find 不加 -type 会把目录也匹配进去** → 找文件加 -type f

## 什么时候该换工具

| 场景 | 用什么 | 为什么 |
|------|--------|--------|
| 按条件找文件 + 操作 | find | 这正是 find 的设计领域 |
| 只想看某个目录占多少空间 | du -sh | find 不擅长求和 |
| 在文件内容里搜关键字 | grep | find 搜文件名，grep 搜内容 |
| 实时监控文件变化 | inotifywait | find 是快照式查找 |

## 换个命令你会了吗？

find 属于**骨架模式 A**：`源 → 过滤 → 目标`。同一模式的命令还有：

- **rsync**：在源和目标之间同步文件——起点、过滤条件、动作，句型完全一致
- **locate**：在文件名数据库里查找——更快的"按名字找"，但需要更新数据库

学完 find，你其实已经掌握了"源→过滤→目标"这一类命令的语法骨架。下次遇到 rsync，先问自己：它的源是什么？过滤条件是什么？动作是什么？
```
