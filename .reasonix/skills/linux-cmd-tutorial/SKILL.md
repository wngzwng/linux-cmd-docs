## 命令类型与章节适配

不同命令类型对标不同的核心章节。写教程时根据命令类型调整侧重点：

### 数据流型（grep, awk, sed, sort, uniq, jq）

> 核心：`文本输入 → 变换规则 → 文本输出`

**侧重点：Layer 2 IO 模型 + Layer 5 Pipeline 组合 + Layer 4 能力轴（匹配/输出/上下文）**

不需要：完整排障复盘通常不需要，IO 模型和 Pipeline 才是主角。

### 查询观察型（find, ps, ss, lsof, df, du, top）

> 核心：`查询对象 + 过滤条件 + 展示方式`

**侧重点：Layer 4 能力轴展开（全轴）+ Layer 6 排障复盘 + Layer 3 语法排雷**

不需要：Pipeline 可简略，IO 模型简单带过。

### 状态管理型（systemctl, kill, chmod, mount, docker, kubectl）

> 核心：`当前状态 → 目标状态 → 执行动作`，通常有对象层级

**侧重点：Layer 2 对象模型（画层级图）+ Layer 3 语法骨架 + Layer 7 踩坑+边界**

不需要：Pipeline 组合通常不适用，IO 模型用对象模型替代。

### 交互型（tmux, vim, htop, less）

> 核心：`会话 + 操作模型 + 快捷键`

**侧重点：Layer 1 场景 + Layer 2 概念模型（会话/窗口/面板层级）+ Layer 4 操作维度**

不需要：IO 模型、Pipeline 组合、"换个命令你会了吗"迁移提示。

## 安全铁律（最高优先级）

> ⚠️ **以下规则优先级高于所有其他写作规则和示例展示。**

**所有涉及删除、覆盖、批量修改等 destructive 操作的示例，必须遵循安全流程，不得直接展示危险命令作为首选示例。**

正确展示模式：

```bash
# 第一步：查看目标范围（-print / --dry-run / echo）
find ./logs -name "*.log" -mtime +30 -print

# 第二步：确认无误后再执行实际操作
find ./logs -name "*.log" -mtime +30 -delete
```

**禁止行为：**
- 直接把 `-delete`、`-exec rm`、`rm -rf`、`mv` 覆盖等作为独立示例的第一行
- 在能力轴展开中单独展示 destructive 参数而不带预览步骤
- 用"当然你也可以直接删"之类的表述弱化安全流程

**允许的唯一例外：** 在 Layer 6「真实排障全流程复盘」中，可以按 定位→确认→预览→执行→复查 的顺序展示完整流程（此时预览和执行在不同步骤中，已隐含安全流程）。

## 命令验证机制

> 当解释具体 Linux 命令参数时，**必须优先参考本机 `man`、官方文档或实际测试结果，不得凭经验推断参数含义。**

### 验证步骤

写教程前，对涉及的每个参数做三轮验证：

1. **存在性验证**：`man <命令>` 确认该参数真实存在，不是凭记忆杜撰
2. **语义验证**：确认参数的精确定义（不是"大概是…"），尤其注意 `+`/`-` 方向、单位默认值、隐式行为
3. **可运行性验证**：每个示例命令在标准 Linux 环境下可直接执行，不会因语法错误直接报错

### 必须标注的系统差异

| 差异类型 | 标注方式 | 示例 |
|---------|---------|------|
| GNU 扩展（非 POSIX） | `> 💡 -maxdepth 是 GNU 扩展，BSD 实现支持情况不同` | find -maxdepth, grep -P, sed -i(无备份) |
| BSD 特有 | `> ⚠️ BSD xxx 的行为是...` | sed -i '' (BSD 要求备份后缀) |
| 行为依赖系统 | `> 在 Linux 上 xxx，在 macOS 上 yyy` | du -h 单位差异、tar 压缩选项 |

### 常见陷阱速查

| 命令 | 容易杜撰的参数 | 实际情况 |
|------|-------------|---------|
| find | `-r`（递归） | find 默认递归，没有 `-r` 参数 |
| grep | 声称 `-r` 是"把输入从单文件扩展为目录树" | 正确（grep 确实有 -r），但注意这是 grep 的 `-r`，不是 find 的 |
| find | `-exec` 是"执行 shell 命令" | 不精确——`-exec` 直接 exec 命令，不经 shell。要 shell 特性（管道、重定向）需 `-exec sh -c '...'` |
| find | `-mtime n` 简化为"恰好 n 天前" | 是"文件数据在 n*24 小时前最后一次修改"，按 24 小时周期取整，非精确到秒 |
| du | `-h` 在所有系统行为一致 | GNU du 和 BSD du 对 `-h` 和 `-d` 的支持不同 |
| ss | 不加 `-t`/`-u` 会显示全部 socket | 不带协议选项时默认只显示部分类型，非所有协议+状态的完整集合 |

## 写作规则速查

### 铁律

0. **安全最高优先级**——任何 destructive 示例必须先展示预览步骤，再展示执行步骤（见上方「安全铁律」）
1. **每条命令至少配一个场景**——没有场景的命令不写
2. **每篇纠正一个流传很广的误解**——用 **加粗 + "不是…而是…"** 句式
3. **给对比**——新手 vs 老手、错 vs 对、低效 vs 高效、场景A用这个 vs 场景B用那个
4. **全文用"你"直接对话**——像面对面教学
5. **💡 小贴士 / ⚠️ 警告**——容易被忽略的细节 vs 可能出错的地方
6. **先验证再下笔**——涉及参数解释前先查 `man` 或实测，不凭经验推断（见上方「命令验证机制」）

### 自检清单

写完后逐条验证：

**安全与真实性：**
- [ ] destructive 操作是否每一步都先给了预览/确认步骤？（铁律 #0）
- [ ] 是否存在单独展示 destructive 参数而不带预览的示例？如有，修正
- [ ] 每个示例命令是否真实存在、参数有效、可直接执行？（命令验证机制）
- [ ] 是否标注了 GNU 扩展 / POSIX 标准 / BSD 特有能力？
- [ ] 每个 ❌ 示例是否真的会报错（不是"不推荐但能跑"）？如果能跑，改标为"不推荐"并注明原因

**内容质量：**
- [ ] 是否至少纠正了一个常见误解？
- [ ] 管道组合中，前一个命令的输出格式是否确实匹配后一个命令的输入格式？
- [ ] 能力轴表是否至少 3 个轴？每个轴是否配了场景？
- [ ] 标题是否有反差感？（"为什么 X 很强，但大多数人…"）

**篇幅适配：**
- [ ] 当前复杂度分级是否符合读者的问题类型？（简单查询不要展开 IO 模型完整图解）
