# linux-cmd-tutorial

> 融合 `linux-cmd-thinking`（五步认知模型）和 `write-cmd-tutorial`（场景叙事风格）的写作方法论。
>
> **核心主张：以五步思维模型为脊椎，以场景叙事为血肉。**
>
> 产出标准：读者看完后不是"记住了参数"，而是"下次遇到这类问题知道怎么思考"。

| 来源 | 提供什么 | 核心金句 |

每个认知步骤穿透一层叙事外衣，最终形成 8 层结构：

```

```

## 一、你会遇到的场景

【真实场景描述——磁盘告警、服务起不来、日志找不到等】

新手的第一反应往往是【笨办法：cd + ls + 手动翻】，运气不好的话能翻半小时。

而真正理解 【命令】 的人，只会敲一行：

```bash
【一行命令干净解决】
```

几秒钟之后，结果一目了然。

**这就是 【命令】 的核心价值：【一句话说清它解决什么问题】。**

## 二、它是怎么工作的——IO 模型

【命令】 的本质不是 `command + options`，而是 `Input → Transform → Output`：

```
【输入】
    │
    ↓ 【处理步骤1】
    │
    ↓ 【处理步骤2】
    │
    ↓ 【处理步骤3】
    │
【输出】
```

> 💡 理解了 IO 模型，很多参数就自然出现了——它们不过是在改变输入来源、处理方式或输出形式。比如 `-r` 就是把输入从"单文件"扩展为"目录树"，`-c` 就是把输出从"匹配的行"变成"数量"。

## 三、语法骨架——先把句型刻进脑子里

```
【命令】  [槽位1：做什么]  [槽位2：对谁做]  [槽位3：怎么输出]
```

属于**骨架模式 【A/B/C/D/E】**（【一句话解释模式本质】）。

⚠️ **在讲具体能力之前，先排一个新手几乎必踩的雷：**

```bash

## 五、Pipeline 组合——把命令串起来

Linux 真正强大的地方不是单个命令，而是管道组合：

```
【命令A】（解决：【局部问题A】）
    │  输出：【格式】
    ↓
【命令B】（解决：【局部问题B】）
    │  输入：【格式】 ← 恰好是上一个命令的输出
    ↓
【命令C】（解决：【局部问题C】）
```

```bash
【管道命令示例】
```

> 💡 这里能串起来的关键是：【命令A】输出的是【格式】，而【命令B】正好接受【格式】作为输入。理解 IO 模型之后，管道组合就是搭积木。

## 六、真实排障全流程复盘

回到开头的场景，完整走一遍：

```
第一步：【定位】  →  【命令 + 解释】
第二步：【确认】  →  【命令 + 解释】
第三步：【预览】  →  【先 print/dry-run，不要直接操作】
第四步：【执行】  →  【实际命令】
第五步：【复查】  →  【验证结果】
```

> 整个过程没有手动【翻目录/改文件/猜测】，全程靠【命令】的条件组合完成【定位→确认→执行→复查】。

## 写作规则速查

### 铁律

1. **每条命令至少配一个场景**——没有场景的命令不写
2. **destructive 操作前先教安全习惯**——`-delete` / `-exec rm` 之前先教 `-print` 确认
3. **每篇纠正一个流传很广的误解**——用 **加粗 + "不是…而是…"** 句式
4. **给对比**——新手 vs 老手、错 vs 对、低效 vs 高效、场景A用这个 vs 场景B用那个
5. **全文用"你"直接对话**——像面对面教学
6. **💡 小贴士 / ⚠️ 警告**——容易被忽略的细节 vs 可能出错的地方

### 自检清单

写完后逐条验证：

- [ ] 是否至少纠正了一个常见误解？
- [ ] destructive 操作是否先给了 dry-run 方式？
- [ ] 每个 ❌ 示例是否真的会报错（不是"不推荐但能跑"）？如果能跑，改标为"不推荐"并注明原因
- [ ] 是否标注了 GNU 扩展 / POSIX 标准 / BSD 特有能力？
- [ ] 管道组合中，前一个命令的输出格式是否确实匹配后一个命令的输入格式？
- [ ] 能力轴表是否至少 3 个轴？每个轴是否配了场景？
- [ ] 标题是否有反差感？（"为什么 X 很强，但大多数人…"）
