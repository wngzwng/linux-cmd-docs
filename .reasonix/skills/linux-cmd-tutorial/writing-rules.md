# 写作规则详解

> 融合两个 skill 的全部写作约束。这些规则不是"建议"，是**验收标准**——每条教程写完后逐条对照。

---

## 铁律

### 1. 每条命令至少配一个场景

没有场景的命令不写。读者需要知道"什么情况下用这个"。

```
# ❌ 没有场景
-t 选项用于按文件类型过滤。

# ✅ 有场景
某天你磁盘满了，想找所有大于 100MB 的日志文件。这时候你就需要 -type f 和 -size +100M 的组合。
```

### 2. Destructive 操作前先教安全习惯

任何带 `-exec rm`、`-delete`、`rm -rf`、`mv` 覆盖等不可逆操作的命令，**第一次出现时必须先教 dry-run 方式**。

```bash
# ⚠️ 安全习惯：在加 -delete 前，先用 -print 确认
find /var/log -name "*.log" -mtime +30 -print   # 先看
find /var/log -name "*.log" -mtime +30 -delete  # 确认无误后执行
```

- 用 `-print` 代替 `-delete`
- 用 `echo` 代替 `rm`
- 用 `--dry-run` 先跑一遍
- 管道中的 destructive 操作同理

### 3. 每篇纠正一个流传很广的误解

用 **加粗 + "不是…而是…"** 句式。这是教程"有深度"的核心标志。

```
> ⚠️ **ctime 不是"创建时间"！** Linux 文件系统不记录创建时间。ctime 是 inode 变更时间——权限改了、硬链接数变了、所有者变了都会更新 ctime。
```

候选误解（按命令）：

| 命令 | 常见误解 | 正确认知 |
|------|---------|---------|
| find | `-ctime` 是创建时间 | ctime 是 inode 变更时间 |
| ss | 不加 `-n` 更快 | 不加 `-n` 反而更慢（DNS + 服务名解析延迟） |
| ss | 看不到进程 = 没有进程 | 非 root 看不到其他用户的进程 |
| ss | `127.0.0.1:8080` 外部也能访问 | 127.0.0.1 只监听本机回环地址 |
| lsof | 只能查文件 | Linux 一切皆文件——socket、pipe 都能查 |
| tar | 选项前的 `-` 必须加 | BSD tar 不需要，GNU tar 可选 |
| du | `du -sh *` 能看到所有文件 | 不包含隐藏文件（`.` 开头），用 `du -sh .[!.]* *` |

### 4. 给对比——四种对比维度

| 对比类型 | 写法 | 示例 |
|---------|------|------|
| 新手 vs 老手 | "新手会…而老手只会敲一行…" | cd + du 翻半小时 vs find 几秒出结果 |
| 错 vs 对 | ❌ / ✅ 代码块对比 | `find . -exec rm {}` vs `find . -exec rm {} \;` |
| 低效 vs 高效 | "其实有更简洁的写法…" | `find . -name "*.go" > files && wc -l files` vs `find . -name "*.go" | wc -l` |
| 场景A vs 场景B | "如果你想 X，用 Y；如果你想 Z，用 W" | "如果找文件看 find，如果搜内容看 grep" |

### 5. 全文用"你"直接对话

像面对面教学。不要用"用户"、"读者"、"我们"。

```
# ✅
你收到磁盘告警。新手的第一反应是...

# ❌
用户收到磁盘告警。新手的反应通常是...
```

### 6. 💡 / ⚠️ 标记规范

| 标记 | 含义 | 使用场景 |
|------|------|---------|
| `💡` | 小贴士 | 容易被忽略但很有用的细节、省时技巧、历史渊源 |
| `⚠️` | 警告 | 可能出错、造成数据损失、服务中断的地方 |

```markdown
> 💡 命令名本身就是线索：`ss` = socket statistics。
> ⚠️ `-delete` 是不可逆的！先用 `-print` 确认。
```

## 自检清单

写完教程后逐条验证：

### 内容完整性

- [ ] 标题是否有反差/好奇感？
- [ ] 开头是否从真实场景切入（而非"X 命令用于…"）？
- [ ] IO 模型是否用流程图描述了输入→处理→输出？
- [ ] 语法骨架是否标注了属于哪一种骨架模式（A/B/C/D/E）？
- [ ] 是否在讲能力之前先排了一个最常见的雷（❌✅ 对比 + 机制解释）？
- [ ] 能力轴表是否至少 3 个轴？
- [ ] 每个能力轴是否配了一个微型场景？
- [ ] 是否至少纠正了一个流传很广的误解（加粗 + "不是…而是…"）？
- [ ] 是否有 Pipeline 组合示例并用 IO 模型解释了"为什么能接起来"？
- [ ] 是否有完整的排障复盘（定位→确认→预览→执行→复查）？
- [ ] 是否有踩坑清单？
- [ ] 是否有工具边界说明（什么时候不该用这个命令）？
- [ ] 是否有迁移提示（同一骨架模式的其他命令）？
- [ ] 结尾是否回到核心观点 + "你平时…"引发思考？

### 技术准确性

- [ ] 每个 ❌ 示例是否**真的会报错**（不是"不推荐但能跑"）？
  - 如果只是"不推荐但 GNU 允许"，改标为"不推荐"并注明原因
- [ ] 是否标注了 GNU 扩展 / POSIX 标准 / BSD 特有能力？
  - 如 `find -maxdepth` 是 GNU 扩展，BSD find 不支持
  - 如 `sed -i` 的语法 GNU 和 BSD 不同
- [ ] 管道组合中，前一个命令的**输出格式**是否确实匹配后一个命令的**输入格式**？
  - 验证边界情况：空格文件名、特殊字符、空输入
- [ ] 所有数字和符号是否正确（`+`/`-` 方向、`\;` 的转义等）？

### 可读性

- [ ] 全文是否用"你"对话（而不是"用户"/"读者"）？
- [ ] 代码块是否有解释说明（而不是干甩一行命令）？
- [ ] 是否有至少 3 处 💡/⚠️ 标记？
- [ ] 是否每层之间有清晰的视觉分隔（标题层级、分割线）？

## 与认知模型的对应关系（写前确认）

在动手写之前，先用 5 分钟完成以下思考，填进 `cognitive-model.md` 的模板：

```
# Command: <命令名>

## 1. Purpose
一句话：它解决什么问题？

## 2. IO Model
输入 → 处理 → 输出
（属于数据处理型还是状态管理型？）

## 3. Grammar
命令 [槽位1] [槽位2] [槽位3]
骨架模式：A / B / C / D / E

## 4. Capability Space
能力轴  | 问题  | 选项
-------|------|-----
...    | ...  | ...

## 5. Scenarios (≥3)
场景1: 需求 → 用到哪些轴 → 命令
场景2: ...
场景3: ...

## 6. Pitfalls
最常见的陷阱（至少1个真正会报错的 ❌ 示例）
```

这 5 分钟的思考 = 教程的骨架。骨架立住了，往叙事模板里填血肉就快。

## 常见写作陷阱（避免）

### 陷阱 1：把能力轴展开写成参数列表

```
# ❌ 参数列表风格
-x: 做X
-y: 做Y
-z: 做Z

# ✅ 能力轴风格
轴1【名称】：它叫什么？ → -name, -iname, -regex
  场景：你记得文件名是"report"，但不确定大小写...
```

### 陷阱 2：开头写"X 是 Linux 中一个强大的命令"

这是正确的废话。读者看了不会产生任何动力继续读。

### 陷阱 3：堆砌参数但不给场景

每个参数都要回答"什么时候用"。

### 陷阱 4：排雷选了太冷门的错误

选 80% 新手会踩的坑，不要选只有 1% 的人会遇到的特例。

### 陷阱 5：管道组合不给 IO 解释

```bash
# ❌ 只有命令，没有解释
find . -name "*.log" | xargs grep "ERROR" | wc -l

# ✅ 带 IO 解释
# find 输出路径 → xargs 把路径喂给 grep → grep 输出匹配行 → wc 计数
```

## 示例真实性检查清单

每个示例命令在写入教程前，必须通过以下 5 项检查：

```
[ ] 命令是否真实存在（man 确认，不是凭记忆杜撰）
[ ] 参数是否属于该命令（如 find 没有 -r，grep 有 -r）
[ ] 示例是否可以直接执行（不会因语法错误直接报错）
[ ] 是否可能造成破坏（如有，必须先展示预览步骤）
[ ] 是否需要增加确认步骤（destructive 操作必有预览）
```

### 常见杜撰参数速查

| 命令 | ❌ 容易杜撰 | ✅ 实际情况 |
|------|-----------|-----------|
| find | `-r`（递归） | find **默认递归**，不存在 `-r` 参数 |
| find | `-exec` 是"shell 命令" | `-exec` 直接 exec，不经 shell |
| find | `-mtime n` = "恰好 n 天前" | 按 24h 周期取整，非精确到秒 |
| grep | `-e` 是"扩展正则" | `-E` 才是扩展正则，`-e` 是指定多个模式 |
| du | `-h` 所有系统一致 | BSD du 不支持 `-d`，用 `-d` 替代 `--max-depth` |
| sed | `-i` 不加后缀 | BSD sed 要求 `-i ''`，GNU sed 允许 `-i` 无参 |
| tar | 选项前的 `-` 可有可无 | BSD tar 不需要 `-`，GNU tar 建议加 `-` 保持兼容 |
